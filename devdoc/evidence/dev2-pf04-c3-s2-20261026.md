## 구현

후보 diff는 [diagnostics](../../crates/engine/src/diagnostics.rs) 한 파일이며 외부 `frozen/candidate/c3.diff`에 보존했다. 계획의 C3 설계를 그대로 따랐다.

- 활성 collector는 64-byte 정렬 `Shard` 4개와 기존 operations/dropped fallback block을 가진다. shard는 owner token, 11 label×started/completed/failed, dropped를 가진다.
- collector id와 thread token은 전역 `AtomicU64`에서 checked 증가로 발급하고 0을 예약한다. 소진되면 0을 받아 항상 fallback을 쓴다. 발급 함수는 전달받은 atomic만 다룬다.
- thread는 const 초기화된 `Cell`에 자기 token과 (collector id, shard 번호 또는 FALLBACK) 한 항목을 둔다. 처음 쓸 때 shard를 찾거나 빈 shard를 0→token CAS로 claim하며, owner는 해제하지 않는다. TLS 접근은 `try_with`이고 실패하면 fallback이다.
- 자기 shard는 Relaxed load→`checked_add(1)`→Relaxed store로 갱신하고, 넘치면 MAX에 두고 saturated를 set한다. fallback은 기존 `fetch_update`다. 모든 drop은 그 thread의 shard 또는 fallback dropped에 기록한다. started→작업→completed/failed 순서와 panic 미완료, Err의 failed 부분집합, full hint 우회는 그대로다.
- snapshot은 label별로 shard4개와 fallback을 checked 합산한다. 합이 넘치면 MAX와 `saturated=true`다. 다음 event sequence는 event lock 아래에서 `emitted + Σdropped + 1`을 checked 계산한다.
- 발급 CAS·shard claim CAS·fallback CAS는 `#[cold] #[inline(never)]` 함수(`issue`, `Collector::claim`, `Collector::increment`)로 분리했다.
- r2는 검토 r1의 비차단 지적을 측정 전에 반영했다. r1에서는 compiler가 `completed`를 inline하지 않아 Off 모드의 Replace도 함수 호출을 거쳤다. 기준선처럼 `#[inline(always)]`로 Off에는 None 검사만 남겼다. claim CAS가 cold 함수에만 있도록 `find`를 강제 inline했다. shard writer가 자기 shard counter만 갱신하는지 debug 단언했다.
- r3는 r2 검토의 차단 지적을 고쳤다. r2에서 `create` 주석을 넣을 때 따옴표 없는 shell heredoc 안의 backtick이 명령으로 실행되어, 주석에 `id` 명령 출력(로컬 계정·그룹 정보)이 들어갔다. r3는 그 한 줄을 편집 도구로 “`id` must return 0 or a freshly issued id” 전제로 고쳤다. 주석만 바뀌어 line 번호도 같고, binary에는 주석 문자열이 들어가지 않는다.
- `logical_bytes`는 `Layout::new::<[usize; 2]>().extend(Layout::new::<Collector>())`의 정렬된 실제 크기와 queue capacity×event 크기다. row quota charge·Snapshot/Cursor 필드·pin 회계·공개 API·형식·controller oracle은 바꾸지 않았고 unsafe·새 dependency도 없다. Off는 collector가 없어 TLS를 읽지 않는다.

## 정적 lock 대조

C3 변경 전에 기준선 release ELF로 식별 규칙과 기준선 지점 목록을 고정했다(외부 `static-rule.json`, `baseline/lock-sites.json`). 지점은 대상 함수의 `lock` 접두 명령과 메모리 `xchg`다. 분류는 line table만 더한 release build의 `objdump -l --inlines` inline 사슬로 정한다. 두 build의 대상 함수 기계어 모양이 같음을 기준선과 후보 모두에서 확인했다.

후보 r1에 적용하는 과정에서 식별 공백3개가 드러났다. 고정 규칙(v1) 그대로는 그 첫 inventory가 미분류1개와 기호 hash 차이로 **불합격**이었다. 보강 `static-rule-amendment-v2.json`은 그 inventory를 본 뒤 썼고, 비교 결과 파일보다 13초 늦게 기록됐다. 클래스 의미와 합격 조건은 바꾸지 않았다. 독립 검토자는 후보 binary 전체 scan에서도 counter `lock` 명령이 cold 함수에만 있음을 별도로 확인했다.

- A1: 후보 r1에서는 compiler가 `Diagnostics::completed`를 inline하지 않고 별도 함수로 남겼다(r2·r3는 inline). 기준선처럼 측정 경로를 덮도록 out-of-line `completed`·`started`를 대상에 더했다. 더 넓게 보는 방향이다.
- A2: 바깥 frame의 compiler 기호 hash(`17h…E`, `.llvm.N`)는 주소처럼 key에서 뺀다.
- A3: 후보는 같은 mutex를 try_lock에서 `0x500(%rsi)`로, unlock에서 `lea` 뒤 `(%rbx)`로 쓴다. 사슬 없는 `xchg`는 같은 함수의 사슬 있는 mutex 명령과 operand가 같을 때 그 unlock이다.

| 분류 | 기준선 | 후보 |
| --- | --- | --- |
| diagnostics counter RMW(대상 경로) | 14 | **0** |
| event queue mutex | 3 | 3 |
| Arc 증감·is_unique | 28 | 28 |
| 기본 metrics `Counters::add` | 2 | 2 |
| Quota | 2 | 2 |
| 미분류 | 0 | 0 |

counter가 아닌 지점의 key 다중집합은 기준선과 같다. 후보의 counter CAS는 cold 함수 `issue`1, `Collector::claim`4(owner claim), `Collector::increment`1에만 있다. 판정은 r1·r2·r3 모두 **PASS**다. r2·r3 비교는 보존한 `tools/compare_v2.py`를 `python3 -B`로 실행했고 plain·line table 기계어 모양 동일도 그 안에서 확인한다. r2·r3의 replace·snapshot·read에서 diagnostics 호출은 기준선과 같은 `record_event`와, collector 존재 검사 뒤 분기 안의 cold 함수뿐이며 r1의 무조건 `completed` 호출은 없다. replace에는 기준선에 없던 unwind 전용 `drop_in_place<Vec<Value>>` 호출이 r1부터 있다. 측정 시간에 대한 주장은 아니며, 원자 명령의 실행 시간은 재지 않았다.
