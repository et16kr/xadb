## 요청과 변경 범위

사용자는 sudo 권한을 확인하고도 해결을 진행하지 않은 점을 지적했고, 중지 요청 뒤 “이어서 해주세요”로 재개했다. 계획 commit `82c14ba`, P1 구현 commit `f22e956`에 이어 실제 PMU 미완료 경로를 보완했다. D2 작업·계약·통합 담당은 `/root`, 독립 검토자는 `/root/pf04_evidence_review`다. 앞선 `sudo perf ... true`는 권한 접근 probe였으며 이번 측정 구간의 증거와 구분한다.

변경 source는 Python runner, 해당 선택 시험, synthetic peer의 활성 구간 중단 fixture3개다. `--perf-privilege sudo-cap-perfmon`을 명시하면 root가 관리하는 sudo/setpriv/perf만 사용한다. sudo는 준비·감독을 위해 EUID0 권한을 가진다. 실행되는 perf는 UID/GID1000, 보조 그룹 없음, CAP_PERFMON(bit38)만5개 capability 집합에 보유하고 no-new-privs=1이다. 고정 최소 환경과 `PERF_CONFIG=/dev/null`을 적용한다.

worker는 UID/GID1000와 기존 그룹·capability 값을 그대로 유지한다. 이 실행 환경은 비활성 CapInh bit35를 이미 상속하지만 permitted/effective/ambient는0이다. 이를 모두0이어야 한다고 잘못 가정했던 첫 실패를 보존하고, caller의 사용 가능한 capability가0이고 worker의 원 상태가 정확히 유지되는지 검사하도록 수정했다. 시스템 `perf_event_paranoid=4`, 설치된 perf의 file capability 없음 상태는 유지했다.

sudo supervisor와 실제 perf collector는 별도 identity로 기록한다. 소유 process group은 기존 bounded cleanup으로, pin한 직접 collector는 pidfd로 종료를 확인한다. 원 group 밖으로 이동한 synthetic collector와 launcher cleanup 오류 주입에서도 해당 collector 종료를 확인했다. 이 보장은 소유 group과 pin한 collector 범위다. 예상외 sudo policy/plugin의 복수·중첩 프로세스 구조는 지원하지 않으며, pin 전에 topology가 거절된 경우 미확인 외부 descendant까지 정리됐다는 증거로 취급하지 않는다. runner 외부 SIGKILL에 대한 finally 실행 보장도 없다.

## 실제 PMU 결과

새 synthetic worker의 enable ACK → GO → 측정 → STOP → disable ACK → perf 종료 경로에서 실제 count를 수집했다. perf version7.0.14, Linux7.0.0-38-generic, sudo-rs0.2.13, setpriv2.41.3 환경이다.

| 이벤트 | raw unscaled count | 보고 coverage |
| --- | ---: | ---: |
| cycles:u | 1,018,558 | 100.00% |
| instructions:u | 5,564,984 | 100.00% |
| ref-cycles:u | 488,825 | 100.00% |
| context-switches | 3 | 100.00% |
| cpu-migrations | 0 | 100.00% |
| page-faults | 1 | 100.00% |

worker의 원 측정 경과 시간은2,211,311ns, worker 경계 부가 길이는7,585ns, runner enable 시작부터 disable ACK까지는6,338,925ns다. counter별 runtime은220,823ns로 보고됐다. 서로 다른 구간·clock 의미를 섞지 않으며 raw PMU에는 제어 경계 작업이 포함된다. 이 자료로 원 K0/영속 실패의 원인을 확정하거나 주파수·개선율을 합성하지 않는다. `performance_acceptance=NOT_APPLICABLE`이다.

정상 실행에서 worker exit0, sudo supervisor SIGINT 종료, 실제 collector pidfd 종료, 두 소유 group 소멸을 확인했다. 특권 모드 receipt의 `perf_finalization.si_code/si_status`는 sudo launcher의 waitid 결과(실제값2/2)이며 실제 perf 자식의 종료 코드는 아니다. 실제 collector는 `pidfd exited=true`만 별도로 확인했다. PMU 활성 상태의 SIGINT·SIGTERM·deadline, READY 전 disabled ACK 직후 중단·identity 거절, 첫 control write/ACK 전 취소도 오류 원문과 종료 상태를 보존했다. 의도한 중단의 runner 결과는 FAILED이며 그 오류·정리를 올바르게 확인한 시험만 PASS다.
