# XADB — 병렬 개발을 위한 파일 구성·소유 정책

2026-10-18 · **채택 정책 / 기존 코드 일괄 재배치·병렬 개발 pilot 미실행**

[관리 JSON](parallel-development-policy.json) · [작업 계약 예시](../examples/task-contract.example.json) · [AI 개발 방법](ai-development-method.md) · [Rust 구현 계약](../contracts/implementation-contracts.md)

**독립적인 기능 변경이 같은 구현·선언·시험 파일에 불필요하게 모이지 않도록 구성한다.** 계층은 의존 방향을 정하고, 계층 내부의 파일은 함께 변경되는 책임을 기준으로 나눈다. 이 문서는 새 코드·변경 코드와 병렬 작업에 적용하는 채택 정책이다. 기존 코드 전체의 재배치나 충돌 감소 실측을 완료했다는 뜻은 아니다.

파일 배치와 작업 조정 규칙을 여기에서 관리한다. 이름·서식·Rust 표현은 해당 코딩 기준을 따르며, 커널 의미와 개발 순서는 기존 구현 계약·단계 계획을 유지한다. Markdown이 규범 원문이고 관리 JSON은 규칙·작업 필드·미실행 인수 계획의 색인이다. 실제 package·디렉터리 배치는 해당 시점의 저장소 정책을 따르며 작업 계약의 계획 경로는 구현 착수 전에 확정한다.

<a id="section-1"></a>

## 1. 파일 구성 규칙

| ID | 규칙 | 적용 기준 |
| --- | --- | --- |
| XADB-LAYOUT-001 | 함께 변경되는 책임별 파일 구성 | 기능 전용 타입·구현·오류·설정 정의·통계·시험을 소유 모듈에 배치 |
| XADB-LAYOUT-002 | 공통 계약의 최소화 | 실제 공유 의미만 공통 경계에 두고 계약 담당과 변경 이유를 명시 |
| XADB-LAYOUT-003 | 작은 조립·등록 지점 | lib.rs·mod.rs·등록 목록에는 연결만 두고 기능 본문은 소유 모듈에 유지 |
| XADB-LAYOUT-004 | 시험과 문서의 책임별 분리 | 모듈 시험·계약 문서는 책임별로, 경계를 가로지르는 시험은 통합 영역에 배치 |
| XADB-LAYOUT-005 | 작업별 수정 범위와 병합 조정 | 수정 경로·공유 파일·계약 담당·동시 작업과 병합 순서를 착수 전에 기록 |
| XADB-LAYOUT-006 | 무관한 정리와 생성물 충돌 방지 | 별도 rename·전체 서식 정리를 기능 변경에 섞지 않고 생성물은 합친 원문에서 재생성 |

**XADB-LAYOUT-001/002:** 같은 계층에 속한다는 이유만으로 무관한 기능을 하나의 `common.rs`, `types.rs`, `manager.rs` 등에 모으지 않는다. 공통 오류의 전달 형식과 모듈별 오류 정의, 공통 설정 읽기 계약과 모듈별 설정 정의를 구분한다. 단순히 두 곳에서 쓰인다는 이유로 foundation으로 올리지 않고 공유 의미·수명·의존 방향이 일치하는지 확인한다. 실제 공통 ID·snapshot·commit·복구 불변식은 기존 단일 소유 계약을 유지한다. 파일 충돌을 줄이려고 이 의미를 모듈마다 복제하지 않는다. 하나의 기능이 여러 계층을 확장하면 필요한 모듈별 변경과 연결 계약을 함께 기록한다.

**XADB-LAYOUT-003:** `lib.rs`·`mod.rs`·server 조립부는 모듈 선언, 좁은 re-export, 명시적 연결을 맡는다. 기능별 정책·거대한 dispatch 본문을 중앙 파일에 누적하지 않는다. 중앙 연결 파일의 작은 수정이 필요하면 공유 변경으로 선언한다. 오류·설정·연산자 등의 registry는 항목 정의를 소유 모듈에 두고 조립 지점에서 합성하는 것을 기본으로 한다. 자동 수집·코드 생성을 실제 도입할 때는 결정적 순서, ID 중복 거절, 누락 검사와 입력·generator identity를 함께 검증한다. 아직 구현된 registry/generator를 뜻하지 않으며 런타임 plugin이나 행마다 동적 dispatch를 강제하지 않는다.

**XADB-LAYOUT-004:** 독립된 책임의 시험을 하나의 거대 `contracts.rs`에 계속 추가하지 않는다. 같은 책임의 unit·계약 시험과 fixture는 가까이 두고, 여러 모듈의 원자성·복구 등을 검증하는 시험은 관련 통합 영역에 둔다. 공통 test helper에는 실제 공유하는 준비 코드만 둔다. 독립 oracle의 의미 계산을 production 코드와 공유하지 않는다. 모듈 계약은 코드 옆과 `devdoc/modules/`의 해당 문서에 연결하고, 전체 개요에는 링크·요약만 유지한다. 기존 파일을 나눌 때 시험의 발견·실행 범위와 증거 ID를 보존한다.

## 2. 작업별 소유와 병합

**XADB-LAYOUT-005:** 사람과 AI에 같은 절차를 적용한다. 작업 담당은 변경·통합을 조정하는 역할이며 일상 편집마다 별도 사용자 승인을 추가하는 규칙이 아니다. [작업 계약 예시](../examples/task-contract.example.json)의 `change_coordination`을 다음 기준으로 구체화한다.

| 필드 | 착수·통합 시 필요한 값 |
| --- | --- |
| `task_owner`, `integration_owner` | 작업과 통합을 담당하는 실제 사람 또는 agent 식별자 |
| `base_identity` | 기준 commit과 미commit 변경 digest. 기존 `source_revision`과 일치 |
| `owned_paths` | 저장소 상대 파일·좁은 glob과 소유 모듈. 계획 경로는 착수 전에 실제 배치에 맞춰 확정 |
| `shared_edits` | 공용 파일·모듈의 경로, 변경 이유, 담당, 선행 병합 단계 |
| `contract_changes` | 영향받는 공통 계약, 계약 담당, 변경 내용과 선행 통합 조건 |
| `overlap_review` | 확인한 동시 작업·기준 identity, 경로 및 의미 중복, 각 중복의 처리 결정 |
| `merge_order` | 공통 계약 → 모듈 구현 → 조립·실제 통합 검사 → 생성물 재생성의 구체 순서 |
| `generated_outputs` | 생성 산출물과 원문, generator 명령, 재생성 담당 |
| `validation` | 모듈 검사·영향받는 실제 통합 검사와 합쳐진 source/build의 증거 |

1. 착수 직전에 최신 작업 트리와 진행 중인 작업의 범위를 읽고 위 항목을 확정한다. 담당 미정·경로 후보·미확인 중복을 완료 상태로 표시하지 않는다. 병렬 작업이 없거나 공통 계약 변경이 없으면 확인 근거와 함께 빈 목록으로 기록할 수 있다.
2. 서로 다른 worktree도 같은 파일·공통 의미를 바꿀 수 있다. 정확한 경로뿐 아니라 디렉터리 포함 관계·glob·rename 전후·공통 API/format/불변식의 중복을 확인한다. 파일이 다르다는 이유만으로 독립 작업이라고 판정하지 않는다.
3. 충돌 가능한 공통 계약·파일 변경은 한 담당이 먼저 반영하고 소비 작업은 그 기준을 가져오거나, 담당별 순차 patch와 병합 순서를 정한다. 같은 공유 작업 트리에서는 동일 파일의 동시 쓰기를 피한다. 겹치지 않는 구현·검토는 계속 진행할 수 있다. 중복이 발견되면 해당 범위의 계약을 갱신한 뒤 수정한다.
4. 통합 담당은 최신 내용을 다시 읽고 자신의 좁은 변경만 적용한다. 다른 작업의 변경을 옛 사본으로 덮어쓰거나 일괄 되돌리지 않는다. text merge 성공 뒤에도 영향을 받는 실제 통합·회귀를 실행하고 합쳐진 source/build identity에 결과를 귀속한다.

## 3. 공유 조립 파일과 생성물

**XADB-LAYOUT-006:** `Cargo.toml`·`Cargo.lock`·모듈 등록·문서 색인·공용 checker도 공유 변경에 포함한다. lockfile은 병합한 manifest를 기준으로 정합성을 확인한다. 원문 Markdown/JSON과 문서 색인을 먼저 합치고 통합 담당이 최신 원문으로 문서 검증 결과를 갱신한다. HTML은 생성하지 않는다. 생성물의 충돌을 수동 편집으로 해결하지 않는다. 재생성 중 입력이 바뀌면 최종 입력으로 다시 생성·검증하며, 오래된 실행 결과를 새 소스의 PASS로 고쳐 쓰지 않는다. 도구로 범위를 정리할 때도 무관한 파일의 rename·서식 변경을 섞지 않는다.

파일 분리는 크기보다 변경 책임과 실제 공동 수정 여부로 판단한다. 현재 foundation의 `runtime.rs`와 통합된 계약 시험처럼 여러 책임을 담은 파일은 관련 작업이 나뉠 때 분리 후보로 검토한다. 일괄 재배치는 이 정책 채택에 포함하지 않는다. 별도 crate는 독립 빌드·공개 경계가 필요한 경우에 검토하고, 순환 의존이나 전역 singleton으로 분리를 우회하지 않는다.

## 4. 적용 확인과 미실행 인수 계획

DEV2 K0 착수 전 해당 작업의 수정 범위·담당·공유 계약을 구체화한다. 이후 실제 병렬 작업마다 중복 검토와 통합 증거를 남긴다. 아래는 개발 절차 인수 계획이며 제품 기능 시험이나 이미 수행한 병렬 실험이 아니다.

| ID | 확인할 작업 | 합격 기준 | 실행 상태 |
| --- | --- | --- | --- |
| PD01 | 같은 기준에서 시작한 독립 기능 두 개 | 기능 전용 변경 경로가 분리되고 필요한 공유 변경은 담당·순서가 기록됨. 합친 결과의 관련 실제 시험 통과 | NOT_RUN |
| PD02 | 같은 파일 또는 공통 계약을 바꾸는 두 작업 | 경로가 달라도 의미 중복을 식별하고 공통 계약을 조정. 조정된 기준에서 소비 작업과 통합 시험 통과 | NOT_RUN |
| PD03 | 문서 원문과 등록·생성물의 동시 변경 | 양쪽 원문 변경을 보존하고 최신 입력에서 생성·검증. 생성물 직접 편집과 다른 작업 덮어쓰기 없음 | NOT_RUN |

병렬 작업 쌍과 기준 revision을 고정하여 기능 전용/공유 경로 중복 수, 실제 merge 충돌 파일 수, 의미 충돌 건수, 조정·재작업 시간을 별도로 기록한다. 공유 조립 파일의 작은 변경과 무관한 기능 본문의 공동 수정을 구분한다. 동일 파일 변경 자체를 merge 충돌로 세거나 서로 겹친 작업자의 시간을 전체 경과 시간으로 합산하지 않는다. 독립 기능 때문에 공용 구현을 반복 수정하면 파일 책임을 재검토한다. 아직 측정값·개선율·일률적인 허용 충돌 수는 없다.

현재 적용 수단은 작업 계약과 리뷰다. 기존 의존성·문서 검사는 파일 응집도, 작업 간 중복, merge 충돌 감소를 자동 판정하지 않는다. 경로 중복 자동 검사와 위 pilot의 실행은 후속이며, 확인하지 않은 검사를 완료로 기록하지 않는다.

## 5. 문서 검증

저장소 루트에서 실행한다.

```bash
python3 devdoc/verify_documents.py
```

문서 검사는 링크·JSON·Markdown 지문 등을 확인하며 제품 시험이나 PD01–PD03의 실행을 대신하지 않는다.
