# XADB — 개발 의사결정과 검증 운영 방침

2026-10-18 · **사용자 위임으로 채택 / 운영 자동화·추가 제품 검증·AI pilot 미실행**

[관리 JSON](development-policy.json) · [AI 작업 절차](ai-development-method.md) · [코딩 기준](coding-convention.md) · [저장소·빌드](repository-build-plan.md) · [단계 완료 계약](../plans/stage-completion.json)

사용자의 “당신의 판단대로 정해 주세요”라는 위임에 따라 개발 방법론·설계 판단 기준·운영 방침을 확정한다. 새 작업부터 적용한다. 기존 제품 방향, 기능 보존 의무, 개발 단계, 커널 불변식과 고객 호환 계약은 유지한다. 이 문서는 DB 알고리즘이나 공개 SQL 의미를 새로 승인하지 않는다.

Markdown은 방침의 규범 원문이고 JSON은 결정 ID·분류·수치 기본값·적용 상태의 색인이다. 기존 실행 결과는 당시 범위의 증거로 보존한다. 아래 수치는 최초 운영을 위한 공학적 기본값이며 통계적 충분성이나 제품 용량·SLA의 측정 결과가 아니다.

## 2. DP01 — 자율 결정과 검토 책임

작업 담당은 착수 때 아래 분류와 적용 근거를 기록한다. 여러 분류가 겹치면 더 강한 검토를 적용한다. 담당과 통합 담당은 작업 계약의 실제 사람 또는 agent 식별자로 지정하며, 단독 작업에서는 같은 담당일 수 있다. 담당자가 비어 있는 예시는 실제 승인 기록이 아니다.

| 분류 | 범위 | 결정·검토 방식 |
| --- | --- | --- |
| D0 | 의미가 바뀌지 않는 문서·링크·서식 | 담당이 자율 수정하고 문서 자동 검사는 push 직전에 적용. 독립 검토 의무 없음 |
| D1 | 확정 계약 안의 구현·버그 수정·리팩터링·회귀 시험 | AI 담당이 자율 구현·검증. 통합 전 별도 검토자 1명이 계약·diff·시험 증거 확인 |
| D2 | 내부 API·사내 형식·공통 계약 구체화, oracle/checker 변경, 의존성 도입, unsafe 예외, 구조·성능 복잡화, 개발 방침 변경 | AI가 대안·선택 근거를 결정 기록으로 작성. 별도 검토자 1명과 해당 계약 담당이 확인하고 통합 담당이 반영. 사용자 확정 방향과 필수 불변식 안에서는 사람의 재승인을 요구하지 않음 |
| D3 | 사용자 확정 제품 방향·기능 보존·호환 의무·필수 품질 기준 변경, 고객 SLA 약속, 외부 출시, 기존 위임 밖의 외부 효과 | 기술 자료와 검증 가능한 결과를 먼저 준비하고 권한 있는 사람의 판단 적용. 같은 범위의 유효한 기존 승인은 재사용 |

이 방침 자체의 채택 근거는 이번 사용자의 명시적 위임이다. 이후 D2 변경의 검토 기록까지 이번 위임으로 대신하지 않는다. 문서에 적힌 제품 의미가 바뀌면 파일 확장자가 Markdown이어도 D0가 아니다. 일상 편집·명령·정상 시험마다 사람에게 허가를 요청하지 않는다.

별도 검토자는 구현자와 다른 사람 또는 별도 AI 실행이다. 구현자의 자기 검토를 독립 검토로 기록하지 않는다. 검토자는 명세·diff·원래 반례·독립 기대값·실제 결과에서 시작하고 구현자의 결론만 전달받아 승인하지 않는다. 같은 모델을 사용할 수 있지만 오류가 통계적으로 독립이라고 가정하지 않는다. 별도 검토 수단이 없으면 구현·로컬 시험은 계속하고 통합 승격을 `READY_FOR_REVIEW`로 남긴다.

의견이 다르면 불변식과 반례로 구분 실험을 수행하고 계약 담당이 D2 범위에서 결정한다. 제품 의도 자체가 불명확하거나 D3 변경이 필요한 경우에만 사람에게 판단을 요청한다. 투표 수나 모델의 자신감으로 결정하지 않는다.

기본 통합 방식은 한 검증 가능한 계약의 작은 변경과 최신 통합 revision의 필수 검사다. 모든 제품 변경은 별도 검토 기록을 남기며 D0는 담당 검증으로 충분하다. PR 도구가 없으면 동일한 diff·검토·결과 기록을 로컬에 남길 수 있지만 보호된 CI나 공식 배포 승격으로 간주하지 않는다. 공유 파일·병합 순서는 [병렬 개발 정책](parallel-development-policy.md)을 따른다.

## 3. DP02 — 결정 상태와 단일 원문

결정 상태는 `PROPOSED`, `ACCEPTED`, `SUPERSEDED`, `REJECTED`로 관리한다. 실행 상태인 `NOT_RUN`, `LOCAL_VERIFIED`, `VERIFIED_PASS`와 분리한다. 채택된 설계도 아직 미구현일 수 있으며 과거 PASS가 새 결정의 검증을 대신하지 않는다.

D2/D3 기록에는 ID, 제목, 상태, 결정일, 담당, 위임·승인 근거, 적용 범위, 비교 대안, 선택 이유, 관련 계약·검증, 검토 기록, 대체한 결정, 재검토 조건을 둔다. D0/D1마다 별도 ADR 파일을 만들 필요는 없으며 작업 기록과 코드 옆 근거로 충분하다. 최초 결정은 기존 소유 문서에 기록하고 독립적인 대안 설명이 필요한 경우 `devdoc/adr/`에 실제 ADR을 추가한다. 빈 문서 트리를 미리 만들지 않는다.

현재 사용자 지시·유효한 위임과 사용자 확정 방향을 먼저 확인하고, 같은 주제의 채택된 소유 계약, 구현 명세, 제안·예시 순서로 해석한다. 이름·위치는 코딩/저장소 정책, 의미는 해당 커널/기능 계약, 호환은 버전 정책, 단계 완료는 단계 계약이 소유한다. 새 문서라는 이유만으로 다른 주제의 계약을 덮어쓰지 않는다. 동급 결정의 충돌은 명시적인 대체 기록으로 해결한다. 실제 코드가 다르면 차이를 결함 또는 변경 제안으로 기록하며 실행 관측만으로 규범을 바꾸지 않는다.

변경 시 원문과 JSON·참조·문서 색인을 함께 갱신하고, 이전 결정은 새 ID 또는 revision과 양방향 대체 관계를 남긴다. 역사적 근거·당시 결과를 현재 상태에 맞춰 다시 쓰지 않는다. 예외는 규칙 ID, 범위, 이유, 제품 검증, 담당, 종료일 또는 재검토 사건을 갖는다. 재검토 조건이 된 예외는 자동 연장하지 않는다. 필수 정확성·복구 검증을 예외 처리로 PASS시키지 않는다.

## 4. DP03 — 변경별 검증 강도

검증 의무는 변경 위험과 현재 capability로 정한다. 단계 완료 계약의 필수 시험·variant가 아래 기본 프로파일보다 우선한다. 과거 DEV0/DEV1 결과를 새 프로파일의 PASS로 소급 변경하지 않는다.

| 프로파일 | 시점 | 필수 범위 |
| --- | --- | --- |
| V0 | 문서 변경을 push하기 직전 | 전송할 commit의 Markdown·JSON·링크·색인/계약 검사. 편집·commit 시 실행하지 않으며 제품 동작 검증으로 보고하지 않음 |
| V1 | 일상 제품 수정 | 수정 전 반례 또는 신규 명세 vector, 수정 후 결과, 경계·오류·인접 정상 사례, 관련 crate 검사 |
| V2 | 제품 변경 통합 | V1 + 현재 capability의 구현된 검사 진입점과 하위 회귀, 영향받는 실제 통합, 해당 변경의 아래 특수 시험. default와 시험 계측 build 구분 |
| V3 | 단계 완료·공식 사내 배포·고위험 확대 검증 | V2 + 동결한 전체 필수 inventory·환경/feature 조합과 해당 확장 시험. 공식 배포에는 실제 release binary와 보호된 증거 검토 추가 |

내구성 변경에는 선언한 모든 commit/checkpoint/recovery fault cut와 독립 ACK 이력·실제 I/O/reopen을, 동시성 변경에는 명시한 schedule과 실제 thread 시험을, 입력/codec 변경에는 잘린·손상·경계 입력과 독립 vector를 추가한다. 자원·취소 변경에는 quota·해제·취소 경합을, 성능 변경에는 DP07 측정을 추가한다. oracle/checker 변경에는 known-bad·잘못된 binary·경로 미도달 등 관련 부정 사례를 요구한다. 안정 릴리스 버전 변경에만 기존 버전 호환 의무를 추가한다.

V2는 미래 기능을 포함한 전체 DEV 단계의 PASS를 요구하지 않는다. 예를 들어 K2의 모듈 통합은 현재 commit 경로를 검사하고 아직 없는 K3 recovery의 의무를 B2에 남긴다. recovery를 제공하거나 B2를 완료한다고 선언할 때에는 실제 reopen 시험을 모두 요구한다. 기존 단계 계약의 모듈 완료·단계 완료 구분을 유지한다.

다음은 새로운 해당 harness에 적용할 초기 시험 예산이다. 해당 종류가 무관하면 이유와 계약을 기록해 N/A로 구분한다. 필요한 harness가 없으면 `NOT_RUN`/미검증 의무이며, 필수 gate를 통과한 것으로 기록하지 않는다.

| 매개변수 | 기본값 | 단위·의미 |
| --- | --- | --- |
| property_merge_seeds | 64 | V2의 고정 seed 수; 각 관련 property/model suite |
| property_merge_max_operations | 128 | seed당 생성 이력의 최대 operation 수 |
| property_extended_seeds | 256 | V3의 고정 seed 수; V2 seed 포함 |
| property_extended_max_operations | 1024 | seed당 생성 이력의 최대 operation 수 |
| real_thread_stress_minutes | 30 | V3의 영향받는 동시성 suite 최소 관측 시간 |
| fuzz_minutes_per_target | 30 | V3의 영향받는 parser/codec target별 최소 fuzz 시간; 보존 corpus는 V2에서도 전부 실행 |
| fault_cell_repetitions | 3 | V3의 각 필수 비결정적 fault 셀을 새 fixture로 반복하는 횟수 |

seed는 목록·generator 버전·hash를 실행 전에 고정한다. operation 최대값을 짧은 이력만 생성하는 이유로 쓰지 않으며 경계 길이의 고정 사례도 넣는다. 작은 상태 기계의 bounded exploration은 actor 수·operation 수·상태/전이 상한을 해당 계약에 명시하고 선언한 유한 공간을 완주해야 한다. seed 시험이나 30분 stress가 그 공간의 전수 검사를 대신하지 않는다. 결정적 fault 셀은 모든 선언 조합을 실행하고, 3회 반복은 미열거 셀을 덮었다는 의미가 아니다.

구체적인 crash cut·schedule·메모리/시간 한도·명령은 해당 leaf 구현 전에 계약 담당이 고정하고 검토한다. 긴 suite는 job으로 분할하되 완료 판정에서는 모든 필수 결과를 합친다. 시간 초과·미도달·오류는 PASS가 아니다. 반복 성공으로 앞선 실패를 지우지 않고, 불안정 시험은 결함·담당·재현 자료를 남긴다. 필수 시험을 제외하려면 동등한 검출 근거를 D2로 검토하며 제품 검증 전에는 승격하지 않는다.

수치 확대·축소는 실행 이전 D2 프로파일 변경으로 관리한다. 현재 실패를 없애려는 사후 축소는 금지한다. 고객 SLA와 제품 최대 용량은 이 예산에서 추정하지 않는다. V3 자동 실행·야간 job은 미구현이다.

## 5. DP04 — 의존성 도입과 갱신

표준 라이브러리와 이미 채택한 dependency를 먼저 검토한다. 검증된 일반 알고리즘·파일 형식·도구를 무조건 재작성하지 않는다. 새 dependency는 실제 사용처, 직접 구현 대비 비용, 공개 API 노출, 전이 dependency·feature, platform/MSRV, allocation·thread·unsafe/FFI·build script, 유지보수·취약점 확인 결과, 대체·제거 경로를 D2 기록에 남긴다. 기본 feature는 필요한 만큼만 켠다. engine 내부 형식·오류·소유권이 외부 crate 타입에 불필요하게 종속되지 않도록 경계를 둔다.

일반 자동 검토 경로의 라이선스 목록은 `MIT`, `Apache-2.0`, `BSD-2-Clause`, `BSD-3-Clause`, `ISC`, `Zlib`로 정한다. 이는 제품의 채택 범위이며 개별 의무 충족을 자동 인증하는 규칙이 아니다. SPDX OR는 실제 선택한 허용 분기를 기록하고 AND는 모든 항의 의무를 확인한다. WITH 예외·출처 불명·목록 밖 조건은 자동 채택하지 않고 기존 회사 승인·권리 근거를 확인한 뒤 필요한 라이선스 담당 판단을 받는다. 동일한 유효 승인을 반복 요청하지 않는다. notice·저작권·소스 제공 등 해당 의무는 실제 배포 manifest와 연결한다.

Rust는 현재 workspace의 직접 버전 고정과 `Cargo.lock`, 도구는 toolchain·image·입력 hash로 고정한다. 이동하는 Git branch를 배포 입력으로 쓰지 않는다. dependency 추가·업데이트마다 공식 변경 내역·보안 공지·라이선스와 실제 지원 feature의 회귀를 확인한다. 보안 권고가 관련되는지 확인하지 못하면 UNKNOWN으로 남기고 공식 배포를 승격하지 않는다. 적용 가능한 알려진 취약점은 수정 버전 또는 검증한 완화책과 책임자의 위험 수용 근거 없이 배포하지 않는다.

버전 갱신은 좁은 변경으로 하고 제품 기능 수정과 무관한 일괄 update를 섞지 않는다. 기존 lockfile 전체 조사 완료를 현재 로컬 개발의 선행 조건으로 만들지 않되 첫 사내 배포 전에는 배포되는 전이 의존성까지 목록·라이선스·공지 확인을 완료한다. 이번에는 dependency를 추가하거나 기존 목록을 감사한 것이 아니다.

## 6. DP05 — AI 개발 방식의 평가와 채택

기본 운영은 현재 설정된 모델의 단일 구현 담당과 DP01의 별도 검토다. 모델명만으로 역할·품질을 확정하지 않는다. 다중 구현 agent·모델 자동 배정·전체 symbol index 같은 추가 장치는 실제 필요한 범위에서 비교 후 채택한다. 병렬 개발의 파일 소유 규칙은 이미 채택되어 있으며 성능 비교가 그 규칙을 중단시키지는 않는다.

첫 pilot은 기능 추가·재현·원인 수정·시험 추가의 4개 과제군에서 각각 개발용 3개와 비공개 평가용 2개, 총 20개 과제로 정한다. DEV1과 실제 구현된 DEV2 capability로 수행 가능한 과제만 만들고, 부족하면 준비 미완료로 남긴다. 성능 최적화 5개는 측정 기반이 생기면, 고객 버전 진화 5개는 고객 기준선이 생기면 추가하여 기존 30개 제안을 단계적으로 적용한다. 비공개 과제를 본 구현 담당에게 같은 과제를 다시 비공개 평가라고 제공하지 않는다.

baseline은 현재 단일 구현 담당의 작업 방식이며 candidate는 문맥 묶음·모델 배정·병렬화 중 한 요인부터 바꾼다. 양쪽에 같은 계약·별도 검토·허용 효과·자원·검증을 적용한다. revision·모델 snapshot/설정·도구·과제·순서·비용 단가와 주 개선 지표(비용 또는 시간)를 실행 전에 고정하고 실행 순서를 무작위화한다. 결과를 본 뒤 유리한 지표로 바꾸지 않는다. 비공개 기대값과 승격은 구현 담당 밖에서 관리한다.

| 매개변수 | 기본값 | 단위·의미 |
| --- | --- | --- |
| pilot_task_wall_minutes | 60 | 과제·방식별 전체 경과 시간; 검토·재시도 포함 |
| pilot_task_total_tokens | 100000 | 모든 agent·재시도를 합한 입력+출력 token 예산 |
| pilot_min_improvement_percent | 20 | 검증 완료 과제당 비용 또는 paired 완료 시간 개선의 잠정 채택 기준 |
| pilot_other_metric_max_regression_percent | 10 | 개선 목표가 아닌 비용/시간 지표의 최대 악화 |

budget을 초과한 시도와 중단도 분모·비용에 포함한다. 정확한 token·비용 관측이 불가능하면 UNKNOWN이며 비용 우월성을 주장하지 않는다. 같은 작업을 제품 개발 목적으로 계속할 수 있지만 초과 후 성공을 원래 pilot 예산 안의 성공으로 바꾸지 않는다.

잠정 채택에는 비공개 과제군마다 baseline 이상의 검증 완료 수, 추가 유출 결함 0, 거짓 PASS·필수 시험 누락 0, 모든 완료 bundle의 새 세션 재현 성공이 필요하다. 품질 조건을 충족한 뒤 위 효율 기준을 적용하며, 시간은 양쪽 모두 완료한 같은 과제끼리 비교한다. 비교 가능한 완료 수가 없거나 개선이 불분명하면 기본 방식을 유지한다. baseline 품질 자체가 필수 계약을 위반하면 먼저 baseline을 고친다.

작은 pilot은 일반적인 우월성의 증명이 아니다. 잠정 채택 후 다음 실제 작업 10개에서 같은 품질 지표·재작업·비용을 확인하고 악화하면 이전 방식으로 돌아간다. 심각한 정확성 결함이나 거짓 PASS가 나오면 10개 종료를 기다리지 않는다. 현재 corpus·비공개 평가·모델 배정 실험은 `NOT_RUN`이다. 기존 routing/execution example JSON은 계속 비활성 예시다.

## 7. DP06 — 공식 사내 빌드와 승격

첫 공식 사내 배포의 qualification 대상은 **Ubuntu 24.04 계열, x86_64-unknown-linux-gnu, 로컬 ext4**로 정한다. 현재 CI의 배포판 계열과 맞춰 초기 조합을 하나로 제한한 선택이며 해당 조합의 DB 내구성 시험 완료를 뜻하지 않는다. 다른 Linux·XFS·네트워크 파일시스템·CPU는 로컬 개발 관측과 제품 지원을 구분하고 별도 시험 뒤 추가한다. 기존 Ubuntu 26.04.1 로컬 결과는 그 환경의 증거로 보존한다.

첫 배포 작업의 담당은 OS 이미지 digest, 실제 kernel·glibc·CPU·장치/가상 디스크의 flush 의미, ext4 mount 옵션, toolchain·lockfile을 구현 전에 구체화한다. 컨테이너 image pin만으로 host kernel·filesystem·장치가 고정되었다고 하지 않는다. toolchain은 현재 `rust-toolchain.toml`의 1.95.0을 유지하고 갱신은 별도 D2 작업으로 한다. clean build와 동등한 의미 재현을 요구하며 binary byte-for-byte 동일성은 현재 보장으로 선언하지 않는다.

| 배포 항목 | 채택값 | 상태 |
| --- | --- | --- |
| 최적화 | opt-level=3, lto=false, codegen-units=16, incremental=false | 첫 배포 recipe에 명시할 값; 현재 manifest 미변경 |
| 오류·진단 | overflow-checks=true, debug=2, strip=none인 원본 보존 | 실제 release 시험·symbol 패키징 미실행 |
| panic | panic=unwind 유지, panic/poison 뒤 엔진 재사용 금지 | 기존 실패 계약 유지; panic 복구를 정상 rollback으로 주장하지 않음 |
| feature | 배포 capability별 명시 allowlist; fault·mutant·test-support 제외 | capability 구현 때 목록 고정; all-features 배포 금지 |
| 설치 | version/target별 tar 묶음과 manifest·checksum·symbol·license notice, 별도 prefix의 설치 smoke | packaging 구현 전; DB 경로와 분리 |

Rust library가 최종 executable의 panic 전략을 단독 결정한다고 가정하지 않는다. embedded/FFI 제공 시 호출자 경계와 panic 전파 방지 계약을 별도로 검증한다. symbol을 분리할 경우 원본·실행 binary·symbol의 대응 hash와 실제 symbolization을 확인한다. 성능 profile 변경도 동일 의미의 release 시험을 다시 수행한다.

보호된 검증은 candidate가 oracle·runner 정책·최종 결과를 동시에 바꿀 수 없는 별도 job/권한으로 운영한다. candidate의 검사 코드 변경은 D2로 먼저 검토하고 보호된 기준을 갱신한 뒤 후보를 검사한다. 통합 필수 check와 검토 기록을 보호 branch에 적용하고, 배포 job은 같은 source·binary·fixture·oracle identity의 V3 증거만 승격한다. 보호 설정·runner·artifact 접근 분리의 부정 시험이 끝나기 전에는 로컬 검증만 주장한다.

사내 배포 bundle과 인수 증거는 배포 후 최소 90일 보존하고 해결되지 않은 결함의 근거는 해결 후 90일까지 유지한다. 안정 릴리스 기준선과 호환 fixture는 해당 major의 지원·호환 의무가 끝날 때까지 보존한다. 현재 CI의 14일 artifact 보관은 공식 배포 증거 보관을 충족하지 않으므로 별도 보관 구현이 필요하다.

## 8. DP07 — 설계 대안과 성능 복잡성

먼저 정확성·원자성·복구·권한·자원 상한·필수 기능을 만족하는 후보만 남긴다. 그 안에서 변경 범위, 실패 의미의 명료성, 독립 재현·관측, 유지보수 비용을 비교하고 필요한 성능을 만족하는 가장 단순한 구현을 기본으로 선택한다. AI token 수·파일 줄 수·crate 수 자체를 목적 함수로 삼지 않는다.

lock-free·unsafe·추가 cache·다중 WAL stream·복잡한 generic/코드 생성 등 비용이 큰 구조에는 실제 요구 또는 profile의 병목, 더 단순한 대안, 예상 이득, 새 불변식·실패 경계·시험·제거 비용을 D2 기록으로 남긴다. 실제 공유 의미 없는 공통화나 사용처 없는 확장 지점은 도입하지 않는다. 초기 단순 구현과 production에서 사용할 수 없는 mock은 구분한다.

분할·공통화 대안에는 코드 양뿐 아니라 새 직접·전이 의존성, 소비자가 이해해야 할 계약, 독립 재현 준비와 관련 통합 비용을 포함한다. 적용 기준은 [코딩 기준 4–5·10절과 XADB-METHOD-001](coding-convention.md#selective-design-reference), 의존성 대조의 원문은 [저장소 정책 4.2절](repository-build-plan.md#dependency-review)이다. 작은 지역 helper의 제한적 중복은 기존 계층 계약 안에서 이유·담당·재검토 조건을 남기고 D1 리뷰로 판단할 수 있다. 공통 계약·의존 경계 변경은 D2이며, 단일 의미 계약의 복제나 독립 oracle의 production 알고리즘 공유는 이 재량에 포함되지 않는다. 파일 수·중복 줄 수·의존성 점수의 감소만으로 필수 정확성이나 실제 측정 비용을 상쇄하지 않는다.

성능 때문에 복잡성을 추가할 때는 동일한 결과·내구성·격리·자원 조건에서 대표 workload를 baseline/candidate로 번갈아 최소 10쌍 측정한다. workload·warmup·표본 길이·CPU/I/O 환경·주 지표·허용 회귀를 측정 전에 고정한다. 이득의 분포·신뢰구간과 p99·메모리·쓰기량·복구 비용을 함께 기록한다. 최소 10쌍은 충분성 보장이 아니며 불확실하면 더 측정하거나 단순한 구현을 유지한다. 모든 변경에 보편적인 5%/10% 향상률을 강제하지 않는다.

2026-10-23 사용자 후속 지시로 **신규 COMM C-V18 성능 시험에 한해** [기본5쌍·편차 시 추가5쌍 계약](../plans/comm-implementation-plan.md#adaptive-repetitions)을 위 최소10쌍의 명시적 예외로 적용한다. 기존 결과를 소급 재분류하거나 다른 DEV 성능 시험의 최소 반복 수를 바꾸지 않는다.

필수 성능 목표 충족 또는 측정 오차와 추가 유지비용을 넘어서는 유용한 개선을 근거로 선택한다. 기능 때문에 필요한 복잡성은 성능 향상 자료 대신 기능 계약·대안·검증 근거를 제시한다. 선택적 복잡성은 이득이 사라지거나 검증 비용이 감당되지 않는 경우 제거·단순화하는 재검토 조건을 기록한다.

## 9. 실행 상태와 남은 구현 입력

이번에 확정한 것은 DP01–DP07의 방침과 초기 기본값이다. 검토자·통합 담당의 실제 배정, 기능별 계약·crash cut·수치 상한, 정확한 image digest·설치 recipe, dependency 감사, pilot corpus는 해당 작업 담당이 이 방침에 따라 구체화한다. 이를 다시 제품 방향의 재승인 요청으로 바꾸지 않는다.

DEV2 K0는 필요한 row/catalog·reference 계약과 로컬 검증으로 진행할 수 있다. 미래 SQL·배포·pilot의 미구현을 K0의 새 선행 조건으로 추가하지 않는다. 단계 완료와 공식 배포에는 기존 [완료 계약](../plans/stage-completion.json)의 모든 필수 입력·검증이 여전히 필요하다. 보호 CI·배포 profile·확장 시험·AI pilot의 실행 상태는 모두 `NOT_RUN`이며 문서 검사로 PASS로 바꾸지 않는다.

문서 자동 검사는 [DOC-002 push 규칙](documentation-policy.md#push-gate)에 따라 전송할 commit에서 실행한다. 편집·commit 때에는 실행하지 않는다. 검증기는 결정·프로파일·수치 색인과 연결, Markdown 지문을 검사하며 실제 운영 집행이나 제품 동작을 검증하지 않는다.
