2026-11-03 · **D3-SCHEDULE-001 / V1 · 사용자 요청에 따른 일정 가중치 기준선 · 독립 D2 ACCEPT · PR 반영 대기**

기준 source: main `f5b731c9`(PR #44 병합). PR 초안은 `cd41b174`(PR #43) 기준 58일·39.66%였다. 병합 전에 PR #44(DELETE 2-b-2) 상태를 반영하고, 사용자 결정으로 01–19 전체를 [공급 단위](#units)로 다시 배정했다([개정 기록](#decision)). 실제 제품 인수 상태는 [단계 완료 정본](stage-completion.json)과 각 source별 증거가 소유한다. 이 문서는 DEV3 일정 보고의 분모·가중치·적립 규칙을 소유한다.

**전체 기준 83일, 완료 적립 28일, 현재 누적 33.73%, 잔여 가중치 66.27%.** 기준선의 남은 중앙 예상 기간은 55일이며, 2026-11-03 뒤 같은 투입을 유지할 때 중앙 완료 예상일은 2026-12-28이다. 낙관/보수 범위는 44~66일(12-17~2027-01-08)이며 확정 납기가 아니다. DELETE는 제품 경로(2-b-2: A 실행기·C preflight/Reserve·B tombstone 읽기·live 정리·replay·loser/winner 복구·base4, 메모리 시험)까지 병합됐으나 2-b-3 관찰자 대조와 3단계 native fault cut이 남아 있어 아직 적립하지 않는다.

## 1. 예상 기간의 의미와 범위

- 기준일은 현재와 같은 AI 구현·별도 검토·통합 방식에서 예상한 경과 기간의 배정 단위다. 인일이나 실제 작업시간 실측값이 아니다. 구현, 관련 fixture/시험, 검토 수정과 통합을 포함한다.
- 완료분 01–05는 2026-11-03에 작업 난도를 보고 **사후 재견적**한 28일이다([공급 단위](#units)). 당시 사전 약속이나 예측 적중률로 해석하지 않는다. Git·기존 검증 기록으로 구분한 실제 경과 약 14일에는 중단·병행·병합 대기가 포함된다.
- 잔여분 06–19는 [공급 단위](#units)로 55일을 배정했다. 1단위는 06(첫 DELETE)의 2일이며, 완료분도 같은 단위로 다시 셌다. PR 초안은 앞서 제시한 28~42일의 중앙 35일을 행마다 2~3일로 거의 고르게 나눴으나, 제한 profile을 일반화하는 행(08·09·11·12 등)과 06의 작업량 차이를 반영하지 못해 병합 전에 대체했다. 단위 계수도 상태 전이·공유 경계·fault/자원 검증 부담으로 매긴 저신뢰 공학적 추정이며, 표의 소수점은 산술 정밀도일 뿐 추정 정확도가 아니다. 잔여 범위 44~66일을 분모에 넣으면 같은 완료 상태가 29.79~38.89%이므로, 33.73%는 이 폭 안의 보고용 기준값이다. 착수 전 분해에서 배정이 크게 모자라면 [6절](#progress-rule)의 V2 절차로 고친다.
- DEV3 저장 엔진과 기존 최종 S5 인수까지 포함한다. 실제 수행한 모듈 분리·필요한 gate 안정화도 포함한다. DEV4 SQL 연결, DEV5–9, 별도 COMM·DEV2 디버깅은 새 작업량으로 넣지 않는다. DEV3 인수에 필요한 하위 공급 의무는 19에서 확인한다.
- 01–05의 완료는 **표에 적은 당시 제한 공급**의 완료다. 일반 기능이나 DEV3 전체가 완료됐다는 뜻이 아니다. 기존 PARTIAL·NOT_RUN·수용된 한계는 원 증거 그대로 남긴다. 표 발급 상한은 10, F6 이후 필요한 성능 개선은 18, 일반 기능·추가 인수는 해당 잔여 행에 있다.
- 모든 새 opcode의 형식·자원 예약(F05)·독립 입력·해당 변경의 복구 검증은 그 행의 구현 전에 준비하고 구현과 함께 검증한다. 이를 12 또는 15–19까지 미루지 않는다. 12는 일반 규모/경계 통합, 15는 독립 audit와 전수 실행 준비, 17–19는 별도 최종 인수 비용이다.

## 6. 앞으로의 누적 % 규칙

1. **고정 분모:** V1의 합계는 83일이다. 완료 ID의 배정일 합계를 분자로 쓴다. `진척률 = 완료 적립일 / 83 × 100`.
2. **한 번만 적립:** 대기·진행 중·검토 중·PR 미병합은 0, 완료 조건을 충족해 main에 들어간 행은 전액이다. 부분 작성량·시험 개수·실제 소요일·경과 날짜로 임의 50%를 주지 않는다. 완료 행의 일부가 후속 기능에서 재사용돼도 원 공급을 다시 적립하지 않는다.
3. **작은 단위로 보고할 때:** 미완료 행을 착수/완료 판정 전에 자식 ID(예: 06-a/b/c)와 각 완료 조건·예상일로 분해한다. 자식 예상일 합은 부모와 같고, 자식 적립을 부모 적립에 다시 더하지 않는다. 이미 달성한 하위 작업에 맞춰 유리한 가중치를 사후 부여하지 않는다. 기존 진행분의 소급 적립이 필요하면 별도 기준선 개정으로 드러낸다.
4. **업데이트할 기록:** 기준일·source, ID 상태, 병합 commit/PR, 실제 착수/종료 또는 미측정, source별 검증·검토 링크, 적립일, 누적률, 남은 ETA를 함께 갱신한다. 증거 본문은 원 구현/증거 문서에 두고 여기는 연결한다.
5. **완료 취소:** 필수 조건을 무효화하는 결함·revert가 확인되면 해당 행을 재개하고 기존 적립을 회수한다. 감소 이유와 이전 값을 남긴다. 진척률이 반드시 단조 증가해야 한다고 강제하지 않는다.
6. **범위 변경:** 실제 소요일 초과만으로 분모를 늘리지 않는다. 신규 기능·필수 의무 추가/삭제 또는 초기 배정의 중대한 오류가 확인되면 V2로 개정하고, 변경 ID·전후 예상일·분모·전후 %·이유·검토를 기록한다. 이전 V1 값과 증거는 Git 이력과 개정표에 보존한다. 완료 인수 의무 변경은 기존 권한/계약을 따른다.
7. **100% 조건:** 01–19의 완료 적립뿐 아니라 [단계 완료 정본](stage-completion.json)의 DEV3 필수 의무와 최종 S5가 닫혀야 한다. 새로 확인된 누락 의무를 숨긴 채 100%를 보고하지 않는다.

예: 06이 전체 완료되면 `(28+2)/83 = 36.14%`, 07도 완료되면 `(28+2+3)/83 = 39.76%`다. 08이 먼저 끝나면 해당 7일만 더한다. 표의 목표 누적률을 건너뛴 작업까지 실제 완료로 읽지 않는다.

보고 형식: `DEV3 V1 / 기준일·commit / 완료 30/83일 = 36.14% / 이번 완료 06(+2.41%p) / 다음 07·08 / 잔여 ETA ○–○일`. %p 역시 원 배정일로 계산하며 표시 반올림의 차이는 최종 누적값을 우선한다.
