# XADB 사용자 매뉴얼 초안

한국어 초안 0.2 · 2026-10-18 · 대상: 애플리케이션 개발자, DBA, 운영자, 기능 구현자

XADB에서 데이터를 조회·변경하고, 설정을 관리하며, 장애를 조사하는 방법을 설명합니다. 먼저 사용하려는 기능의 상태를 확인한 뒤 작업 절차와 결과 확인 방법을 함께 읽으십시오.

**현재 사용할 수 있는 구현은 DEV0 검증 도구와 DEV1 공통 기반입니다. DB 엔진·SQL·서버·사용자용 `xadb` CLI는 아직 구현되지 않았습니다.** 이 초안의 제품 사용 절차는 구현할 동작의 명세 초안이며, 실행 가능한 배포판의 설명서는 아닙니다. 아래의 `xadb`와 SQL 예제는 모두 **문법 제안·실행 미검증**입니다.

[현재 개발 단계](../plans/development-stages.md) · [인터페이스 기준안](interface-experience-plan.md) · [초기 SQL 명세와 기대 결과](sql-language-draft.md) · [초안의 요구사항·출처·예제 관리](user-manual-draft.json)

## 1 이용 안내

### 읽는 순서

| 목적 | 먼저 읽을 내용 |
|---|---|
| XADB를 처음 이해하기 | 2장 제품 개념 → 3장 설치와 첫 접속 → 4장 SQL 시작 |
| 애플리케이션 만들기 | 5장 자료형과 SQL → 6장 트랜잭션 → 10장 연결과 드라이버 |
| 운영 자동화하기 | 8장 설정 → 9장 CLI와 자동화 → 11장 권한 |
| 느린 요청 조사하기 | 12장 상태·성능 → 13장 메시지·진단 → 17장 문제 해결 |
| 장애와 데이터 이동 준비하기 | 14장 백업·복구 → 15장 복제·전환 → 16장 이관·업그레이드 |

### 설계 상태와 지원 상태

설계가 정해졌다는 것과 설치한 버전에서 사용할 수 있다는 것은 다릅니다. 이 초안은 다음 두 가지 상태를 구분합니다.

| 축 | 표시 | 의미 |
|---|---|---|
| 명세 | 설계 기준 | 현재 채택한 XADB 계약을 사용자 관점에서 설명 |
| 명세 | 제안 | 이름·문법·기본값 등 공개 명세 확정 전의 안 |
| 명세 | 미정 | 기능별 명세와 인수 조건을 더 정해야 함 |
| 구현 | 로컬 검증 | 명시된 작은 구현 범위만 실제 로컬 시험됨 |
| 구현 | 미구현 | 사용 가능한 제품 기능으로 안내할 수 없음 |
| 구현 | 제품 검증 | 해당 배포 버전의 실제 경로·환경·인수 증거가 있어야 표시 가능 |

2026-10-18 기준 구현 상태는 다음과 같습니다. DEV 번호는 개발 단계이며 제품 버전 번호가 아닙니다.

| 범위 | 현재 상태 | 목표 개발 단계 |
|---|---|---|
| 독립 테스트 도구와 공통 ID·값·오류·파일 경계 | DEV0·DEV1의 유한 범위 로컬 검증 | DEV0·DEV1 |
| 트랜잭션·영속성·복구 커널 | 미구현 | DEV2 |
| DISK 행·색인 | 미구현 | DEV3 |
| embedded SQL과 로컬 SQL 도구 | 미구현 | DEV4 |
| 네트워크 서버·인증·세션 | 미구현 | DEV5 |
| native client·JDBC·ODBC | 미구현 | DEV6 |
| 확장 SQL·프로그래머블 객체 | 미구현 | DEV7의 기능별 작업 |
| 복제·운영 도구·관리 화면 | 미구현 | DEV8의 기능별 작업 |
| 파티션과 디스크 partition global index | 미구현 | PART·NG 및 SQL·서버 통합 |

한 단계가 끝났다는 이유로 그 단계의 모든 최종 기능을 지원한다고 해석하지 않습니다. 배포 버전의 기능 목록에는 실제 지원 범위, 제약, 검증한 환경을 기록해야 합니다. 사내 버전은 안정 릴리스 전 개발·검증용이며 외부 출시 자격을 뜻하지 않습니다.

### 예제 사용 규칙

예제의 `lab-orders`, `orders`, `C-41`, `OP-38`은 가상 대상입니다. 제안된 출력은 설명용이며 실제 실행 결과가 아닙니다. 비밀번호·인증 토큰·운영 데이터는 예제에 넣지 않습니다. SQL 예제는 4장의 생성·적재 초안을 전제로 하며, 실행 검증된 배포용 샘플은 아직 없습니다.

### 구현자가 이 문서를 사용하는 순서

해당 기능의 매뉴얼 절차 → 연결된 상세 계약 → 정상·실패 기대 결과 → 실제 구현·시험 순서로 읽습니다. 채택된 개발 순서·커널·복구·버전 계약이 우선하며, 이 문서에서 새로 제안한 필드·문법은 구현 전에 상세 명세로 확정합니다. 충돌이 있으면 기존 계약을 조용히 바꾸지 않고 관련 Markdown·JSON을 함께 수정합니다.

각 기능은 지원 단계와 권한, 입력·기본값·한도, 성공 결과, 오류 후 문장·거래·자원 상태, 취소·재시도, 검증 예제를 갖춰야 합니다. `미정`은 임의의 기본값을선택하라는 뜻이 아닙니다. 19장의 결정 목록에서 해당 기능에 필요한 항목만 먼저 해결하며, 후속 기능의 미정 사항이 초기 커널 개발을 막지는 않습니다.

## 2 제품 개념과 구성

### 데이터베이스와 접속 대상

데이터베이스는 테이블·색인·사용자 데이터의 논리적 관리 단위입니다. 인스턴스는 데이터베이스를 서비스하는 실행 단위입니다. 세션은 접속한 사용자의 실행 맥락이며, 요청은 SQL이나 관리 동작 한 번을 뜻합니다. 트랜잭션은 여러 변경을 함께 확정하거나 취소하는 단위입니다.

접속 정보에 붙인 이름을 **context**라고 부르는 안을 사용합니다. context는 접속 편의를 위한 이름입니다. 실제 작업 전에 서버가 반환한 DB·인스턴스 identity, 접속 사용자, 권한을 확인해야 합니다. `prod`라는 이름이나 화면 색상만으로 운영 대상과 권한이 보장되지는 않습니다.

### DISK

XADB의 제품 저장 방식은 DISK이며 영속 데이터입니다. 버퍼에 올라온 페이지도 같은 디스크 객체의 캐시입니다. 현재 K0의 volatile 개발 상태는 이 영속 저장 기능의 구현 증거가 아닙니다.

초기 SQL은 비파티션 DISK 테이블을 대상으로 합니다. 후속 PART 단계에서는 하나의 논리 테이블을 여러 디스크 파티션으로 나누는 기능을 개발합니다. 애플리케이션은 논리 테이블을 사용하고 운영자는 파티션별 배치와 자원 사용량을 확인합니다.

### 사용자 도구

| 제안된 접점 | 사용하는 목적 |
|---|---|
| `xadb sql` | 대화형 SQL과 SQL 파일 실행 |
| `xadb config`, `xadb activity`, `xadb logs` | 설정·현재 활동·메시지 조사 |
| 관리 화면 | 개요에서 요청·객체·설정·사건·작업으로 이동 |
| 공개 SQL 조회 영역 | 객체 설명과 운영 상태를 SQL로 조회 |
| native client·JDBC·ODBC | 애플리케이션에서 데이터베이스 사용 |

운영 메시지 로그는 오류·시작·설정 변경 등을 설명하는 자료입니다. 복구에 사용하는 WAL과 역할이 다릅니다. 메시지 파일을 보관했다고 데이터베이스를 복구할 수 있는 것은 아닙니다.

## 3 설치와 첫 접속

**설계 기준과 제안 절차 / 제품 설치 명령 미정.** 현재 소스 빌드는 DB 서버 설치가 아닙니다. 다음 절차는 설치·서버 기능을 제공하는 배포판에서 완성할 사용자 흐름입니다.

### 설치 전에 준비할 것

1. 배포판에 명시된 Linux·CPU·라이브러리·파일시스템 조합을 확인합니다. 현재 개발 호스트의 구성만으로 제품 지원 환경을 판단하지 않습니다.
2. 설치 계정, 데이터 위치, 자원 예산, 접속 대상, 인증 방법을 정합니다. 기존 DB가 사용하는 위치를 새 DB 생성 경로로 지정하지 않습니다.
3. 소프트웨어·데이터·복구 자료·백업·진단 자료의 공간을 각각 계획합니다. 버퍼와 작업 메모리 사용량에도 트랜잭션·쿼리·복구·진단에 필요한 여유를 포함합니다.
4. 기본 권한과 자격 증명 보관 방법을 준비합니다. 이 초안은 기본 관리자 암호나 고정 포트를 지정하지 않습니다.


### 설치 후 확인 순서

패키지 식별 정보 확인 → 설치 위치 준비 → 새 DB 생성 조건 검사 → 설정 검증 → 시작 → 준비 상태 확인 → 인증된 접속 → 실제 SQL 결과 확인 순으로 진행합니다.

서버 프로세스가 실행 중이라는 사실만으로 접속 준비가 완료된 것은 아닙니다. 상태 화면에서 준비 단계·마지막 진행 시각·오류를 확인합니다. 복구 중이면 아직 일반 쿼리를 받지 않을 수 있습니다.

접속한 뒤에는 DB·인스턴스 identity, 사용자, 읽기·쓰기 권한, autocommit, 트랜잭션 상태를 확인합니다. 초기 embedded SQL에서는 네트워크·TLS 절차 대신 해당 로컬 실행 대상을 확인합니다.

### 접속에 실패했을 때

확인 순서는 주소/DNS → 연결 경로 → TLS → 인증 → 권한 → 서버 준비 상태입니다. 진단 도구는 실제로 확인한 범위만 보고해야 합니다. 응답이 없다는 이유만으로 암호 오류나 DB 부재로 단정하지 않습니다.

SQL에 접속할 수 없으면 OS 권한 안에서 로컬 상태·초기 메시지·설정 오류를 확인합니다. 인증서 검증을 끄거나 DB 경로를 새로 만드는 방식으로 원인을 숨기지 않습니다.

### 시작과 종료

정상 종료는 새 요청의 입장을 제한하고 기존 요청·트랜잭션의 처리 상태를 확인하는 절차를 포함합니다. 대기 시간 초과와 강제 종료를 구분하고, 다시 시작한 뒤 준비 상태와 이전 작업의 결과를 확인합니다. 구체적인 시작·종료 명령과 timeout 기본값은 후속 명세에서 확정합니다.

<a id="manual-lifecycle"></a>
### 기동·종료 절차의 판정표

**동작 기준 / 상태 표시 이름 제안.** 서버 수명과 관련된 최소 기동·종료 기능은 DEV5에서 조립하고, 운영 자동화는 DEV8에서 확장합니다. 설치·삭제 명령은 아직 정해지지 않았습니다.

| 단계 | 전제와 수행 | 성공 확인 | 실패 시 남길 상태 |
|---|---|---|---|
| 새 DB 준비 | 설치/build 확인, 비어 있는 소유 경로·권한·용량 검사 | 생성 대상과 설정 검증 결과 확보 | 기존 DB/지원하지 않는 형식이면 변경 전 거절; 자동 초기화 금지 |
| 시작 | DB identity와 설정 출처 확인, 단일 소유 실행 조건 검사 | 복구의 PREFLIGHT → SELECT → LOAD → SCAN → REPLAY → VERIFY → READY 진행과 마지막 진행 시각 | 실패 단계·오류·진행 여부 보고; 부분 복구 상태로 일반 SQL 제공 금지 |
| 접속 확인 | READY 뒤 업무 계정으로 연결 | 실제 DB identity·권한 확인, 4장 fixture 조회의 타입·행 일치 | 상태 조회 성공과 SQL 실행 성공을 구별 |
| 정상 종료 | 새 입장 제한, 진행 중 요청·거래 drain, 정해진 대기 예산 적용 | 서버의 종료 완료와 프로세스 종료 확인 | 대기 만료는 종료 실패/진행 중으로 보고; 강제 종료로 자동 전환하지 않는 안 |
| 강제 종료 후 재시작 | 마지막 관측 거래·작업 ID 보존, production recovery 수행 | ACK를 받은 commit과 원자성 검증, READY 확인 | 미확인 commit은 UNKNOWN; 이전 작업을 임의 재실행하지 않음 |

프로세스 생존 확인과 서비스 준비 확인을 구분합니다. supervisor가 복구 중이라는 이유만으로 재시작을 반복하지 않도록 진행 시각·허용 대기·복구 실패를 구별하는 운영 정책이 필요합니다. 빈 경로라는 검사 결과는 검사 순간의 정보이므로 실제 생성 시에도 소유권·동시 실행을 다시 검사해야 합니다.

배포 파일 제거와 DB 데이터 폐기는 별도 작업으로 제안합니다. 제거 절차에는 서버 종료, 백업 보존, 데이터·설정·로그·자격 증명의 잔존 위치를 명시합니다. 재설치가 기존 DB 삭제 동의나 사내 버전 변환을 의미하지 않습니다. 관련 인수 계획: MA-01, MA-02.

## 4 SQL 시작하기

**목표: DEV4 embedded SQL 이후 / 문법 제안·실행 미검증.** 이 장은 간단한 조회와 트랜잭션의 의미를 설명합니다.

### 샘플 데이터

논리 테이블 `orders`에 다음 열과 행이 있다고 가정합니다. 초기 타입을 사용하고, 문자 길이는 아래의 byte 단위 제안을 따릅니다. 날짜·정밀 금액 타입은 후속 예제에서 다룹니다.

| 열 | 논리 타입 | 조건 |
|---|---|---|
| `order_id` | signed 64-bit 정수 | 기본 키, NULL 불가 |
| `customer_name` | UTF-8 text | NULL 허용 |
| `quantity` | signed 64-bit 정수 | NULL 불가 |
| `paid` | BOOLEAN | NULL 불가 |

| order_id | customer_name | quantity | paid |
|---:|---|---:|---|
| 1001 | 김하나 | 2 | FALSE |
| 1002 | NULL | 1 | TRUE |
| 1003 | 빈 문자열 | 3 | FALSE |

여기서 NULL, 길이가 0인 문자열, 네 글자인 문자열 `NULL`은 서로 다른 값입니다. 다음 생성·적재 구문을 초안으로 제안합니다. 이름·타입·문법·오류의 정확한 선택 사항은 [초기 SQL 명세](sql-language-draft.md)에 연결합니다.

<!-- manual-example: EX-10 -->
**문법 제안·실행 미검증**

```sql
CREATE TABLE orders (
    order_id BIGINT NOT NULL,
    customer_name VARCHAR(80),
    quantity BIGINT NOT NULL,
    paid BOOLEAN NOT NULL,
    PRIMARY KEY (order_id)
) STORAGE DISK;
INSERT INTO orders (order_id, customer_name, quantity, paid)
VALUES (1001, '김하나', 2, FALSE),
       (1002, NULL, 1, TRUE),
       (1003, '', 3, FALSE);
```

이 초안에서 `VARCHAR(80)`은 최대 80 UTF-8 bytes이며 `STORAGE DISK`는 영속 DISK 테이블을 지정합니다.  기존 동명 테이블을 자동 삭제하는 예제는 제공하지 않습니다.

### 행 조회하기

<!-- manual-example: EX-01 -->
**문법 제안·실행 미검증**

```sql
SELECT order_id, quantity
FROM orders
WHERE paid = FALSE
ORDER BY order_id;
```

설계상 기대 결과는 `(1001, 2)`, `(1003, 3)`입니다. 실제 엔진에서 얻은 출력은 아닙니다. 예제를 제품 검증으로 전환할 때는 열 타입·정렬·행 개수까지 확인해야 합니다.

NULL인 이름만 찾을 때는 `customer_name IS NULL` 조건을 사용합니다. `customer_name = NULL`을 참·거짓 비교처럼 해석하지 않습니다. 문자열 출력에서 빈 문자열과 NULL이 같아 보이면 출력 형식의 NULL 표현을 확인합니다.

### 변경을 되돌려 보기

<!-- manual-example: EX-02 -->
**문법 제안·실행 미검증**

```sql
BEGIN;
UPDATE orders SET quantity = 5 WHERE order_id = 1001;
SELECT quantity FROM orders WHERE order_id = 1001;
ROLLBACK;
SELECT quantity FROM orders WHERE order_id = 1001;
```

같은 트랜잭션 안의 첫 조회는 자신의 변경인 5를 봅니다. 다른 동시 변경이 없는 샘플에서 rollback 이후 새 조회는 원래 값 2를 봐야 합니다. 변경을 보존하려면 rollback 대신 commit을 사용하며, 성공 확인과 응답 유실의 차이는 6장을 따릅니다.

샘플 테이블 생성·삭제 같은 DDL은 초기 명시적 DML 트랜잭션 안에서 실행하지 않습니다. 지원되지 않는 조합은 명시적 오류로 거절해야 하며 숨은 commit으로 처리하지 않습니다.

### 실패한 문장 다음의 상태 확인

아래는 SQL-06과 같은 독립 사례입니다. 4장 초기 fixture를 새로 만든 뒤, 예상된 오류를 확인하고 다음 문장을 진행하는 대화형 또는 시험 controller에서 사용합니다. 기본 `--on-error stop` 파일 실행으로 모든 문장이 실행된다고 가정하지 않습니다.

<!-- manual-example: EX-11 -->
**문법 제안·실행 미검증**

```sql
BEGIN;
UPDATE orders SET quantity = 5 WHERE order_id = 1001;
INSERT INTO orders (order_id, customer_name, quantity, paid)
VALUES (1004, '이둘', 1, FALSE), (1001, '중복', 1, FALSE);
SELECT order_id, quantity FROM orders ORDER BY order_id;
ROLLBACK;
```

기대: INSERT는 unique 오류이며 1004도 저장되지 않습니다. 같은 거래의 SELECT는 `(1001, 5), (1002, 1), (1003, 3)`입니다. 앞선 UPDATE는 아직 미commit 상태로 유지되고 마지막 ROLLBACK으로 취소됩니다. 다른 세션에서는 미commit 값 5가 보이지 않아야 합니다. 문장 성공의 affected row count는 commit 성공 응답이 아닙니다.

## 5 자료형과 SQL 참고

### 초기 타입의 의미

| 논리 타입 | 초기 의미 | 주의할 경계 |
|---|---|---|
| signed 64-bit 정수 | -9,223,372,036,854,775,808부터 9,223,372,036,854,775,807 | 범위를 넘는 연산은 오류이며 wrap하지 않음 |
| BOOLEAN | 참·거짓, nullable 열에서는 NULL도 가능 | 숫자·문자와의 암묵 변환을 가정하지 않음 |
| UTF-8 text | 정규화 없는 UTF-8 byte 기준 비교 | 표시가 같아도 byte가 다르면 같지 않을 수 있음 |
| binary | byte 값 | 문자 인코딩 변환을 임의로 적용하지 않음 |
| NULL | 값의 부재 | 빈 문자열·0·FALSE와 구별, 비교는 3값 논리를 따름 |

SQL 타입의 제안 철자는 `BIGINT`, `BOOLEAN`, `VARCHAR(n)`, `VARBINARY(n)`입니다. 가변 길이의 n은 byte 수이며 초과하면 오류입니다. 암묵 변환과 자동 잘림을 허용하지 않습니다. UNIQUE는 NULL이 포함된 키끼리 충돌시키지 않고, PRIMARY KEY는 NULL을 허용하지 않는 안을 사용합니다. 빈 문자열은 값이므로 UNIQUE에서 중복을 검사합니다.

DEV1 공통 라이브러리의 가변 값 상한 64 KiB와 연결해 초기 사내 SQL의 n 범위를 1–65,536으로 제안합니다. 이를 최종 SQL 열 길이·LOB·제품 용량의 지원 한도로 선언하지 않습니다. 이 선택들의 상세와 반례는 [초기 SQL 명세](sql-language-draft.md#section-2)에 있으며 구현 전 검토할 신규 제안입니다.

### 초기 SQL 범위

| 종류 | DEV4 목표 | 최초 범위에 포함하지 않는 것 |
|---|---|---|
| 객체 정의 | 비파티션 테이블·색인의 생성과 삭제 | 트랜잭션 안 DDL, 고급 온라인 DDL |
| 변경 | INSERT·UPDATE·DELETE | 확장 MERGE·반환 구문의 모든 조합 |
| 조회 | 한 테이블의 열 선택·조건·정렬·limit | join·집계·subquery·window |
| 제약 | 기본 키·UNIQUE·NOT NULL | FK·CHECK |
| 트랜잭션 | BEGIN·COMMIT·ROLLBACK·autocommit | 명시적 SAVEPOINT |

지원 범위 밖의 구문은 안정된 미지원 오류로 거절합니다. 성공한 것처럼 무시하거나, 일부 의미만 조용히 실행하지 않습니다. 초기 범위에서 보류된 기능도 기존 업무 대체에 필요한 경우 최종 요구에 남습니다.

### 확장 SQL과 프로그래밍 기능

정밀 수치·날짜·시간·추가 문자 처리, join·집계·분석 함수, PSM·package·cursor·trigger·sequence·job·queue, LOB·공간 데이터, 외부 routine·DB link·XA 등은 후속 기능별 참고서에서 다룹니다. 사용할 수 있는 버전·입력 범위·권한·오류 효과를 각 항목에 명시해야 합니다. 이 초안은 해당 구문이나 호환 API를 새로 정의하지 않습니다.

### 참고서 항목의 읽는 법

완성할 SQL 참고서의 각 항목은 목적 → 문법 → 인자와 기본값 → 반환값 → 권한 → 트랜잭션 효과 → 오류·취소 → 제약 → 예제 순서로 구성합니다. 함수·옵션이 문서에 이름만 있는 상태를 구현 지원으로 해석하지 않습니다.

### 자주 혼동하는 입력과 결과

| 입력 또는 선택 | 이 초안의 의미 | 구현·이관 시 확인 |
|---|---|---|
| `orders`, `ORDERS`, `"orders"` | 같은 이름; `"Orders"`는 다른 이름 | 인용 이름의 정확한 UTF-8 비교, 128-byte 사내 한도 제안 |
| `VARCHAR(6)`에 `'가나'` / `'가나다'` | 각각 6 / 9 UTF-8 bytes | 앞은 허용, 뒤는 길이 오류; 자동 잘림 금지 |
| 정수 열에 `'12'` | 문자열이므로 타입 오류 | driver도 숫자 문자열을 몰래 cast하지 않음 |
| `ORDER BY` 없음 / 정렬 키 동률 | 순서 미보장 / 동률 순서 미보장 | 페이지·LIMIT 재현에는 unique key까지 정렬 |
| `ASC` / `DESC`의 NULL 위치 생략 | 각각 NULLS LAST / NULLS FIRST 제안 | scan과 index 경로의 결과 일치 |
| 같은 값으로 UPDATE | 조건에 맞은 행을 affected count에 포함 | 변경 byte 수나 commit 수로 해석하지 않음 |
| WHERE 없는 UPDATE·DELETE | 모든 행 대상 | 도구 경고가 SQL 의미를 바꾸지 않음 |

초기 SQL에서는 산술식·함수·`SELECT 1`·OFFSET·출력 alias를 이용한 ORDER BY도 미지원입니다. 상태 점검에 `SELECT 1`을 기본 예제로 쓰지 않고, 4장의 지원되는 fixture 조회를 사용합니다. 전체 문법과 예상 오류는 [SQL 명세](sql-language-draft.md), 경계 사례 SQL-18–25는 그 문서의 7절을 따릅니다.

## 6 트랜잭션과 오류 처리

### 자동 확정과 명시적 트랜잭션

사용자 SQL 도구의 기본안은 autocommit 켜짐이며 프롬프트에 항상 표시합니다. 여러 변경을 하나의 단위로 묶으려면 명시적 트랜잭션을 사용합니다. autocommit·timeout·격리 수준은 접속이나 풀에서 세션을 얻을 때 확인합니다.

초기 격리 기준은 고정 snapshot과 보수적인 충돌 검증을 사용하는 SERIALIZABLE입니다. 자신의 변경은 같은 트랜잭션에서 읽을 수 있습니다. 충돌하면 전체 트랜잭션을 다시 시작해야 할 수 있습니다. READ COMMITTED·REPEATABLE READ의 세부 업무를 초기 격리 수준만으로 대체 완료했다고 보지 않습니다.

### 문장 오류와 트랜잭션 오류

| 관측된 상황 | 설계상 효과 | 다음 행동 |
|---|---|---|
| 복구 가능한 다중 행 문장의 타입·unique 오류 | 이번 문장 효과를 되돌림, 이전 성공 문장은 트랜잭션에 남을 수 있음 | 오류의 transaction effect를 읽고 입력 수정 또는 rollback |
| commit 충돌 | 트랜잭션 전체 ABORTED | 새 snapshot에서 전체 업무를 재시도할지 판단 |
| 확정 전 안전한 경계에서 취소 완료 | 명세한 문장 또는 트랜잭션 범위의 취소 | 취소 범위와 최종 효과를 확인 |
| commit 결과 불명 | COMMITTED/ABORTED를 아직 확정할 수 없음 | 결과 확인 경로를 사용하고 자동 재실행 보류 |
| 영속 commit 이후 접속 종료 | 이미 확정된 변경은 유지 | 재접속을 rollback 증거로 삼지 않음 |

`COMMITTED`, `ABORTED`, `UNKNOWN`은 결과의 의미를 설명하는 명칭입니다. 정확한 wire field·SQLSTATE·오류 번호는 후속 공개 명세에서 정합니다. `UNKNOWN`은 실패의 다른 이름이 아닙니다.

### 응답을 받지 못했을 때

1. DB·인스턴스, 요청·트랜잭션·작업 ID, 관측 시각과 마지막 확인 상태를 보존합니다.
2. 설치 버전이 제공하는 결과 조회 범위와 기록 보존 기한을 확인합니다.
3. 확인된 결과에 따라 후속 업무를 진행합니다. 조회 결과 없음·보존 만료·권한 제한은 미실행을 증명하지 않습니다.
4. 확인할 수 없으면 업무 키 등 인가된 조회와 운영 절차로 결과를 대조합니다. 일반 SQL request ID만으로 중복 방지가 보장되지는 않습니다.

### 종료와 취소

Ctrl-C의 요청 취소, 트랜잭션 rollback, 세션 종료는 별개입니다. 취소를 요청했다는 응답과 실제 효과가 되돌려졌다는 확인도 구분합니다. commit과 취소가 경합하면 실제 확정된 결과를 따릅니다.

대화형 종료에서는 미완료 트랜잭션을 보여 주고 commit·rollback·계속 중 선택하는 안을 사용합니다. 비대화형 정상 종료는 활성 미commit 트랜잭션의 rollback을 요청하고 확인한 상태를 보고합니다. 연결 유실이나 강제 종료로 확인하지 못한 rollback을 완료라고 표시하지 않습니다.

<a id="manual-transactions"></a>
### 세션 상태 전이와 재시도 판단

**SQL 초안의 세부 제안.** `IDLE`과 `ACTIVE`는 현재 세션 상태이고 `COMMITTED`·`ABORTED`는 종료한 거래의 결과입니다. 마지막 거래가 COMMITTED여도 다음 문장을 기다리는 세션은 IDLE입니다. 결과의 확실성과 세션 상태를 하나의 값으로 합치지 않습니다.

| 시작 상태 | 요청 | 성공 또는 거절 뒤 상태 |
|---|---|---|
| IDLE, autocommit ON | SELECT/DML | 문장별 거래 시작·종료; 결과와 마지막 거래 효과 보고 |
| IDLE, autocommit OFF | 첫 SELECT/DML | ACTIVE; 조회만 해도 snapshot과 자원을 유지할 수 있음 |
| IDLE, ON/OFF | BEGIN | ACTIVE; 종료 후 기존 autocommit 설정 유지 |
| ACTIVE | 복구 가능한 문장 오류 | 이번 문장만 복원; 이전 성공 문장과 ACTIVE 유지 |
| ACTIVE | BEGIN, autocommit 변경, DDL | 명시적 상태 오류; 기존 거래 유지, 숨은 commit 없음 |
| ACTIVE | COMMIT 성공 / ROLLBACK 성공 | IDLE; 종료 결과 각각 COMMITTED / ABORTED |
| IDLE | COMMIT / ROLLBACK | 상태 오류; 존재하지 않은 거래의 성공 결과 생성 금지 |
| IDLE, autocommit OFF | DDL | 독립 원자 작업으로 확정; OFF라는 이유로 미commit DDL로 표시하지 않음 |

commit 충돌은 전체 거래를 ABORTED로 끝냅니다. 새 거래에서 필요한 읽기를 다시 수행하고 업무 조건을 다시 판단해야 합니다. 마지막 UPDATE만 반복하면 옛 snapshot에서 계산한 결정을 재사용할 수 있습니다. 외부 결제·파일·메일 같은 효과는 DB rollback에 포함되지 않으므로 전체 업무 재시도 가능 여부를 별도로 판단합니다.

client가 응답을 잃은 UNKNOWN과 엔진의 영속 I/O 결과 불명은 구분합니다. 전자는 client가 모르는 동안 서버 거래는 끝났을 수 있습니다. 후자는 커널 계약에 따라 새 writer를 차단하고 recovery로 판정합니다. 모든 네트워크 timeout을 DB 전체 쓰기 차단으로 해석하지 않으며, I/O 불명 상태를 일반 문장 오류로 처리하지도 않습니다.

오류 응답에는 최소한 오류 코드, 문장 효과, 거래 효과, 결과 확실성, 재시도 단위, 연결 재사용 가능 여부가 필요합니다. 코드만 보고 재시도하지 않습니다. MA-03과 SQL-06·08·13–16으로 이 경계를 확인할 계획입니다.

## 7 테이블과 저장 배치와 색인

### 객체 정의 확인

테이블을 만들거나 변경하기 전에 열·NULL·기본 키·제약과 저장 매체를 확인합니다. 색인은 접근 경로와 제약을 제공하므로 행 변경과 함께 일관되게 유지돼야 합니다. 같은 이름으로 객체를 다시 만들면 이전 객체와 다른 identity/generation입니다. 오래된 핸들이나 변경안을 그대로 재사용하지 않습니다.

### 파티션과 global index

| 속성 | 설명 |
|---|---|
| 논리 테이블 | 애플리케이션이 조회하는 하나의 객체 |
| 파티션 | range·list·hash 등 명세한 분할 규칙에 따른 데이터 범위 |
| 저장 매체 | 각 파티션·색인의 DISK 배치 |
| local/global 범위 | 색인이 다루는 행의 논리적 범위 |
| unique | 선언한 논리 범위에서 키 중복을 허용하는지 여부 |

global이라는 이름을 DISK 전용이라는 뜻으로 사용하지 않습니다. 파티션·매체가 다르다는 이유로 같은 논리 unique key의 중복을 허용하지 않습니다. 파티션 로컬 unique와 테이블 전체 unique는 별개 계약입니다.

디스크 저장은 테이블 상세에서 파티션 배치 → 색인 범위 → 자원 사용 → 접근 경로 → 변경 영향을 확인하는 흐름으로 운영합니다. 색인의 물리 저장 위치와 LOCAL/GLOBAL 논리 범위를 구분합니다.

### 객체 변경의 완료 확인

초기 offline 색인 생성·bulk partition 작업은 DB 전체 admission을 닫고 기존 사용자의 drain을 확인한 뒤 시작하는 계약을 따릅니다. 해당 작업의 중단 범위와 timeout을 사전에 확인합니다. 온라인 이동·자동 tiering은 별도로 지원·검증되기 전까지 사용할 수 있는 기능으로 표시하지 않습니다.

변경 후에는 정의·행/색인 일관성·관련 작업 상태·오류를 확인합니다. 진행률을 알 수 없으면 마지막 진행 시각과 현재 단계로 판단하며 임의의 퍼센트나 종료 시각을 사용하지 않습니다.

<a id="manual-storage"></a>
### 저장 공간·오래된 snapshot·offline 작업

데이터 크기와 서버 전체 메모리 사용량은 다릅니다. 현재 데이터, 오래된 snapshot이 보존하는 버전, 미commit 변경·예약, DISK buffer, checkpoint·recovery 여유, 진단 비용을 나눠 확인합니다. SQL 결과를 천천히 읽는 cursor나 오래 열린 거래도 과거 자료의 회수를 지연시킬 수 있습니다.

quota 초과는 정해진 오류 효과와 예약 반환을 확인할 수 있는 경로입니다. OS OOM·프로세스 abort는 같은 의미의 정상 rollback이 아닙니다. 종료한 프로세스의 미commit 변경과 ACK를 받은 commit은 재시작 복구로 판정합니다. 제품 최대 행·key·table·partition 수와 동시 cursor·pin 예산은 아직 미정이며 DEV1 값 길이 한도를 제품 용량으로 사용하지 않습니다.

초기 offline 색인 생성의 절차는 대상·generation·권한 확인 → DB 전체 admission 차단 → 기존 사용자 drain → build → 행·색인 검증 → 원자 공개 → admission 복원입니다. drain timeout이면 build를 시작하지 않습니다. 실패 시 기존 정의와 가시 행을 유지하고 새 임시 자원을 회수해야 합니다. admission 복원은 운영자가 별도로 설정한 차단까지 해제하는 뜻이 아니며 작업이 소유한 차단만 해제하는 안입니다.

DROP·partition 제거·행 이동은 오래된 reader가 보던 행과 새 접근의 대상을 구분합니다. 논리 삭제 완료와 물리 공간 회수 완료를 각각 표시해야 합니다. 객체를 같은 이름으로 재생성해도 이전 ID를 새 객체로 재사용하지 않습니다. row 이동을 애플리케이션의 행 삭제·재삽입으로 표시하거나 global unique 범위를 파티션별로 축소하지 않습니다. 관련 인수 계획: MA-04, MA-05.

## 8 설정 관리

**제안된 이름:** `memory.limit`, `query.timeout`, `logging.level`. 이 명칭과 기본값은 아직 공개 명세로 동결되지 않았습니다.

### 값과 출처 확인

설정을 볼 때 현재 유효 값, 저장된 희망 값, 적용 대기 값, 단위, 적용 범위, 출처, 적용 시점을 함께 확인합니다. `0`, `auto`, `unlimited`, `unset`은 같은 뜻이 아닙니다. 각 설정의 설명에서 의미를 확인해야 합니다.

설정 범위의 제안 순서는 기본값 → 인스턴스 → DB → 역할 → 세션 → 실행 한정 값입니다. 실제로 지원하는 범위만 적용합니다. 같은 인스턴스 범위 안에서는 선택한 영속 소유자의 값 → 허용된 환경변수 → 허용된 시작 옵션 순으로 우선하는 안을 사용합니다. 상위 자원·보안 정책을 하위 값으로 우회하지 않습니다.

<!-- manual-example: EX-03 -->
**문법 제안·실행 미검증**

```text
ax config explain query.timeout --context lab-orders --format json
```

이 조회에서 확인할 것은 숫자 하나가 아니라 현재 값·출처·범위·적용 시점입니다. 권한 때문에 출처의 파일 위치를 볼 수 없는 경우도 구분합니다.

### 설정 변경 절차

1. 목적과 관련 설정, 현재 값과 실제 출처를 확인합니다.
2. 변경 대상과 값·단위·적용 범위를 지정하고 검증합니다.
3. 기존 세션·새 세션·재시작에 미치는 영향과 자원 조건을 검토합니다.
4. 검토한 대상 identity와 설정 revision이 유지되는지 확인한 뒤 적용합니다.
5. 저장 상태와 현재 상태를 비교하고, 필요한 새 세션 또는 재시작 후 다시 확인합니다.

파일 관리 모드는 검증과 수정안 내보내기를 제공하는 안이며, 제품 내 관리 모드는 CLI·관리 동작·화면에서 같은 변경을 수행하는 안입니다. 두 저장소를 번갈아 덮어쓰지 않습니다.

상위 환경변수에 가려진 값을 저장해도 현재 값은 바뀌지 않을 수 있습니다. 다음 시작 때의 환경변수·옵션을 모르면 다음 시작 예상 값은 미확정입니다. 묶음 변경이 일부만 적용됐다면 항목별 결과와 남은 조치를 확인합니다.

### 변경을 되돌릴 때

이전 값을 쓰는 것도 새로운 변경입니다. 이미 종료된 세션이나 완료한 업무를 과거 상태로 되돌리는 것은 아닙니다. 임시 override가 만료되면 그때의 기본 설정과 남은 override로 유효 값을 계산합니다. 과거 값을 강제로 덮어쓰지 않습니다. 재시작·생성 시 고정 설정에 즉시 원복되는 TTL을 가정하지 않습니다.

<a id="manual-settings"></a>
### 설정 참고서의 최소 항목과 변경 사례

설정 이름만 구현하지 않고 다음 정보를 설정 사전과 CLI·화면에서 함께 제공합니다. 다음은 필드 계약 제안이며 기본값·상한의 숫자를 확정한 것은 아닙니다.

| 항목 | 필수 설명 |
|---|---|
| 정의 | 안정된 이름, 목적, 타입·단위, 허용 범위, 기본값 또는 계산 규칙과 버전 |
| 의미 | `0`·음수·`unset`·`auto`·`unlimited` 허용 여부와 각 효과; 모르는 값은 거절 |
| 범위 | 지원하는 인스턴스/DB/역할/세션/요청 범위와 상위 정책 한도 |
| 현재 상태 | 유효 값, 저장 값, 대기 값, 출처, 가려진 값, 관측 시각·revision |
| 적용 | 즉시/새 세션/재적용/재시작/생성 시 고정 중 하나, 기존 요청·거래 영향 |
| 변경 | 필요한 권한, 관련 설정의 결합 제약, 변경 ID·작성자·이유, 되돌리기의 효과 |

`query.timeout`의 상세 제안은 기간 단위의 실행 예산입니다. 정확히 언제부터 시간을 재는지(admission 대기·실행·fetch 포함 여부), 단위 정밀도·반올림, 취소 응답 지연, client 대기 timeout과의 관계를 구현 전에 확정합니다. 예산이 끝났다는 사실만으로 rollback 완료를 반환하지 않습니다. `memory.limit`는 상한의 대상·공유 메모리 계산·recovery 여유가, `logging.level`은 sink별 적용·감사와의 분리가 정해져야 이름만으로 서로 다른 동작이 구현되는 것을 막을 수 있습니다.

**가상 변경 사례:** 재시작 적용 설정의 현재 값이 8 GiB이고 영속 저장 값을 12 GiB로 바꿨다고 가정합니다. 결과는 `저장=12 GiB / 현재=8 GiB / 재시작 대기`입니다. 환경변수가 10 GiB로 덮어쓰면 그 출처를 함께 표시합니다. 다음 시작의 환경을 모르면 예상 값을 확정하지 않습니다. 이 수치·재시작 방식은 설명용 가정이며 `memory.limit`의 확정 기본값이나 적용 방식이 아닙니다.

검토한 revision 뒤에 다른 변경이 생기면 충돌을 보고 새 차이를 검토합니다. 일부 항목만 적용된 묶음은 성공한 항목·실패한 항목·대기 항목을 모두 반환합니다. 자동 원복 지원 여부를 사전에 명세하며 과거 값을 무조건 덮어쓰지 않습니다. 관련 인수 계획: MA-06, UX-03·18·27.

## 9 CLI와 자동화

### 명령 찾기

| 제안 명령군 | 목적 |
|---|---|
| `xadb context`, `xadb connect`, `xadb status`, `xadb doctor` | 접속 대상과 준비 상태 확인 |
| `xadb sql`, `xadb object` | SQL 실행과 객체 설명 |
| `xadb config`, `xadb activity`, `xadb query` | 설정·활동·쿼리 조사 |
| `xadb logs`, `xadb error`, `xadb diagnose`, `xadb support` | 메시지·오류·제한 진단·지원 묶음 |
| `xadb operation` | 긴 작업 조회·대기·허용된 취소 |
| `xadb backup`, `xadb restore`, `xadb replication` | 백업·복원·복제 작업 |
| `xadb data`, `xadb migration` | 논리 데이터 이동·변환·비교 |

자동화에서는 context를 명시하고 개인 PC에서 최근 선택한 대상을 사용하지 않습니다. 암호를 인수로 넣는 대신 명세한 인증 저장소·프롬프트·제한된 자격 증명 경로를 사용합니다.

### SQL 파일 실행

<!-- manual-example: EX-04 -->
**문법 제안·실행 미검증**

```text
ax sql --context lab-orders --file check.sql --on-error stop --format json
```

`check.sql`은 4장의 조회처럼 이 버전이 지원하는 문장만 담는 파일을 뜻합니다. 비대화형 기본안은 오류에서 중단입니다. 앞에서 이미 commit한 문장까지 자동으로 원복되지는 않습니다. 단일 트랜잭션 옵션이 추가되더라도 DDL·외부 효과를 포함한 임의 스크립트의 원자성을 가정하지 않습니다.

기계 출력은 locale·색상·터미널 폭에 영향받지 않아야 합니다. stdout에는 선택한 결과를, stderr에는 진행과 사람용 진단을 출력하는 안입니다. 큰 정수·NULL·binary를 손실 없이 표현하는 방식은 공개 출력 명세에서 정합니다.

### 출력 완료와 작업 완료

유한 `json`은 단일 결과 문서입니다. 대량 출력용 `jsonl`은 타입·행·문장 결과·최종 결과를 구별합니다. 유한 출력에 최종 결과가 없으면 완료로 처리하지 않습니다. CSV는 데이터 외의 완료 receipt 또는 CLI 종료 결과를 확인해야 합니다.

파일 생성이나 일부 행 수신은 성공 증거가 아닙니다. 출력 디스크 부족·broken pipe와 서버에서의 commit을 구분하십시오. commit 후 출력이 실패했다면 DB 변경이 보존된 상태일 수 있습니다. 다음 문장을 보내지 않고 이미 실행 중인 요청의 확인 가능한 결과를 따릅니다.

### 긴 작업과 재접속

작업 접수 응답은 완료 응답이 아닙니다. operation ID를 저장하고 상태를 조회합니다. 기다리기 timeout은 서버 작업 취소를 뜻하지 않습니다.

<!-- manual-example: EX-05 -->
**문법 제안·실행 미검증**

```text
ax operation wait OP-38 --context lab-orders --timeout 5min
```

접수 응답 자체가 유실되면 operation ID도 모를 수 있습니다. 해당 동작이 제출 키 조회·중복 방지를 지원한다면 **전송 전에** 키와 대상을 보존합니다. 같은 키의 같은 내용은 하나의 작업으로 연결하고 다른 내용은 거절하는 계약을 사용합니다. 권한 범위·보존 기한·재시작 후 조회 범위를 확인해야 합니다.

기록이 없거나 보장 기한이 지났다고 같은 작업을 자동 재제출하지 않습니다. 결과 불명 상태를 유지하고 실제 효과를 확인합니다. 일반 SQL request ID는 이 제출 키 계약을 자동으로 갖지 않습니다.

<a id="manual-cli-results"></a>
### 자동화 결과의 구조와 손실 없는 값

**공개 출력 상세 제안 / 정수 종료 코드 배정 미정.** 각 결과는 최소한 다음 정보를 분리합니다. 같은 필드를 CLI·관리 API가 사용할지는 기능별 명세에서 확정하되 의미는 유지합니다.

| 제안 필드 | 타입·의미 |
|---|---|
| `schema_version`, `target`, `request_id` | 출력 형식 버전, 실제 대상 identity, 요청 식별자; 부팅을 넘는 ID 범위 명시 |
| `action_status` | `accepted`, `succeeded`, `failed`, `incomplete`, `unknown`; 접수와 완료 구분 |
| `delivery_status` | `complete`, `partial`, `failed`; 결과가 client 출력에 전달된 정도 |
| `statement_effect` | `not_started`, `no_change`, `applied`, `rolled_back`, `unknown`; applied는 거래 내부의 문장 효과이며 commit 증거가 아님 |
| `transaction_state` | `idle`, `active`, `unavailable`; 현재 세션 상태, 조회만 해도 active 가능 |
| `transaction_effect` | `none`, `committed`, `aborted`, `unknown`; 해당 요청이 거래에 남긴 효과, 현재 세션 상태와 별도 |
| `error`, `retry_scope` | code·effect·certainty와 재시도 단위; 원문 비밀과 다른 사용자의 존재 정보 제외 |
| `operation_id`, `statement_results` | 긴 작업 ID, 각 문장의 순번·결과·오류·affected rows; 적용 안 되는 항목은 사전 규칙에 따라 생략 |

BIGINT의 JSON 값은 부호 있는 10진 **문자열**과 열 타입 metadata로 표현하는 안입니다. `9223372036854775807`을 부동소수 JSON 소비자에서 반올림하지 않아야 합니다. BOOLEAN은 JSON boolean, SQL NULL은 JSON null, 빈 text는 `""`, 문자열 NULL은 `"NULL"`로 구분합니다. binary는 대문자 짝수 hex 문자열과 binary 타입 metadata로 표현하고 빈 binary도 타입으로 구별합니다. 열은 순서 있는 metadata 배열, 행은 같은 순서의 값 배열로 제안하여 중복 출력 열 이름을 JSON object의 중복 key로 잃지 않게 합니다.

`jsonl`의 제안 레코드 종류는 `metadata`, `row`, `statement_end`, `request_end`입니다. 레코드에는 문장/결과 집합 ID와 순번을 연결합니다. 빈 결과도 metadata와 완료 레코드가 필요하며, 유한 요청은 `request_end`의 상태를 검사합니다. 알 수 없는 필수 형식 버전·레코드 종류는 성공으로 무시하지 않습니다. 알려진 버전의 추가 optional 필드는 무시 가능하게 설계합니다. 열린 로그 stream은 이 유한 SQL 결과 규칙과 별도입니다.

종료 결과의 분류는 정상 완료, 입력·권한 등 실행 전 거절, 확정된 실행 실패, 결과 불명, 출력 전달 실패, 대기 시간 만료로 제안합니다. **0은 요청한 CLI 동작의 정상 결과가 완전하게 전달된 경우에만** 사용합니다. 제출 명령의 0과 `accepted`는 서버 작업 완료를 뜻하지 않고, wait의 완료 조건은 terminal 상태입니다. 서버 효과가 UNKNOWN인 경우 다른 오류가 함께 있어도 상세 결과에서 UNKNOWN을 지우지 않습니다. 숫자 배정·동시 오류 우선순위·필수 필드·크기 상한은 MS-03에서 확정합니다.

SQL 오류로 스크립트가 중단되면 실행한 문장 수·실패 순번·마지막 거래 효과를 반환하고 아직 보내지 않은 문장은 미실행으로 표시합니다. 출력 실패 시 이미 서버에 보낸 요청을 미실행으로 바꾸지 않습니다. pipeline에서는 가능한 환경에서 각 프로세스 종료 결과를 확인하며, CLI가 강제 종료되어 반환값 자체가 없으면 완료 불명으로 처리합니다. 관련 인수 계획: MA-07, MA-08, UX-09·26.

## 10 애플리케이션 연결과 드라이버

**목표: DEV6 이후 기능별 제공 / driver 배포·URL·API 상세 미정.** native client → JDBC → ODBC 순서로 구현하는 계획입니다. 동일한 이름의 API가 존재한다는 이유만으로 모든 표준 기능을 지원한다고 가정하지 않습니다.

### 연결 수명 관리

연결 설정 준비 → 서버 identity·인증 확인 → 기능·타입·metadata 확인 → 트랜잭션 정책 확인 → 요청 실행 → 결과·오류 효과 확인 → 결과 자원 정리 → 연결 반환 순서로 사용합니다.

연결 풀에서는 이전 사용자의 미완료 트랜잭션·세션 설정이 다음 사용자에게 남지 않도록 반환 조건을 확인해야 합니다. 결과 불명인 연결을 정상 연결처럼 돌려주거나, 재접속 뒤 마지막 변경 문장을 자동 반복하지 않습니다.

### 값을 전달할 때

문자열로 SQL을 조합하는 대신 해당 드라이버가 지원·검증한 인자 바인딩을 사용합니다. NULL과 빈 문자열, 정수 범위, UTF-8 byte 길이, binary 표현을 확인합니다. decimal·날짜·시간대·LOB 등은 그 타입을 지원하는 버전과 API가 준비된 뒤 사용합니다.

### timeout의 구분

| 종류 | 의미 | 실패 뒤 확인 |
|---|---|---|
| 연결 대기 | 접속·인증 완료를 기다리는 한도 | 서버 세션 생성 여부와 연결 상태 |
| SQL 실행 제한 | 요청 실행에 적용되는 제한 | 취소 접수와 실제 문장·거래 효과 |
| 결과 읽기·네트워크 대기 | client가 응답을 기다리는 한도 | 서버 실행·commit 여부는 별도 확인 |
| 작업 대기 | 이미 접수한 긴 작업의 완료를 기다리는 한도 | 서버 작업은 계속 진행할 수 있음 |

각 옵션의 정확한 이름·단위·기본값과 SQLSTATE 대응표는 드라이버별 참고서에서 확정합니다. client timeout만으로 서버 rollback을 단정하지 않습니다.

<a id="manual-clients"></a>
### 드라이버 구현과 사용의 공통 계약

| 기능 | 사용자에게 제공할 계약 | 실패·경계에서 확인할 것 |
|---|---|---|
| prepare·bind | 인자 위치/이름·타입·NULL 표시·byte 길이·수명, 지원 여부 | bind 값과 SQL 텍스트 분리, 범위 초과·잘림의 명시적 오류 |
| 결과 metadata | 열 순서·이름·논리 타입·nullable·정밀도·길이 단위 | 같은 이름의 두 열도 보존, 숫자·binary의 손실 없는 전달 |
| fetch·cursor | fetch 단위·버퍼 예산·종료 방법·commit 후 cursor 수명 | 부분 결과와 끝 표시 구분, close/cancel/disconnect 후 자원 회수 |
| batch·array | 원자 단위, 중단/계속 정책, 원소별 결과, commit 단위 | 일부 성공·미실행·불명 원소 구분; 여러 문장을 단일 문장처럼 취급하지 않음 |
| 오류·취소 | native/JDBC/ODBC의 동일한 효과·certainty·재시도 의미 | SQLSTATE와 native code를 모두 보존, 취소 요청 접수와 취소 완료 분리 |
| pool 반환 | 미완료 결과 정리, 거래 종료 확인, 세션 설정 초기화 | 초기화 실패·결과 불명 연결은 재사용하지 않음; 몰래 commit 금지 |
| 재접속 | 새 연결의 identity·capability·세션 설정 재확인 | 옛 cursor·prepared handle·미commit 거래를 이어받지 않음 |

드라이버별 표준 API에서 자동 확정 전환·close 등의 부작용이 요구되는 경우에는 서버 SQL의 `SET AUTOCOMMIT` 상태 오류 규칙과 구분하여 명세합니다. 표준 API의 동작을 임의로 바꾼 채 표준 지원이라고 표시하지 않습니다. adapter가 보내는 commit/rollback과 응답 유실 시 효과까지 시험해야 합니다. 정확한 JDBC/ODBC 표준 범위·URL·패키지·SQLSTATE는 MS-06에서 확정합니다.

**batch 예:** B1·B2·B3의 세 INSERT를 보냈고 B1 commit 후 B2 unique 오류로 중단했다면, B1=committed, B2=실패·효과 없음, B3=미실행으로 보고합니다. 명시적 하나의 거래 안에서 같은 입력을 처리했다면 B1은 아직 ACTIVE일 수 있습니다. 하나의 다중 행 INSERT는 4장처럼 문장 전체가 되돌려집니다. 드라이버가 전송 단위를 묶었다는 사실만으로 이 세 경우를 같은 원자 단위로 약속하지 않습니다.

연결 검사는 서버 준비·네트워크 확인과 실제 SQL 실행을 구분합니다. DEV4 최소 SQL에는 `SELECT 1`이 없으므로 드라이버의 health 검사 전략도 지원 capability에 맞춰야 합니다. MA-09·10과 SQL-06을 실제 driver 경로에 연결할 계획입니다.

## 11 사용자와 권한과 보안

사용자·역할·권한은 대상 DB와 실제 업무 범위를 기준으로 관리합니다. 일반 사용자, 관측자, 운영자, 설정 관리자, 보안·감사 담당, 지원 진단의 업무를 구분하는 안을 사용합니다. 정확한 role 이름과 권한 조합은 아직 미정입니다.

자신의 세션 조회와 타인의 SQL 원문 열람은 별도 권한입니다. 화면에서 숨긴 값이 SQL 뷰·CLI JSON·오류 detail·로그·지원 묶음에서 다시 노출돼서는 안 됩니다. 공유한 조사 링크도 받는 사람의 권한을 확인해야 합니다.

권한을 변경하거나 작업을 취소할 때는 현재 대상과 권한을 다시 확인합니다. 같은 이름으로 재생성된 객체, 재사용된 세션 번호, 변경된 context 주소에 오래된 변경안을 적용하지 않습니다.

인증서·자격 증명은 배포판이 지원하는 방식으로 보관합니다. 기본 계정 암호, TLS protocol/cipher 목록, 암호화 저장 기능과 key 관리 절차는 후속 보안 명세·검증 범위에서 정합니다. Linux 전용이라는 조건이 제품 보안 검증을 대신하지 않습니다.

### 감사 기록의 실패

감사는 운영 메시지와 권한·보존·실패 정책을 구분합니다. 필수 감사 기록을 남길 수 없으면 보호 대상 관리 동작을 시작 전에 거절하는 것이 기본안입니다. 이미 실행된 뒤 결과 기록에 실패했다면 **동작의 실제 효과와 감사 저장 상태**를 따로 확인합니다. 감사 실패를 이유로 같은 변경을 자동 재실행하지 않습니다.

<a id="manual-security"></a>
### 최소 권한과 인증서 교체 절차

다음은 제품 role 이름이 아닌 **업무 권한 분리안**입니다. SQL·CLI·화면·로그·지원 묶음에 같은 제한을 적용합니다.

| 업무 | 필요한 권한 범위 | 별도 권한으로 남길 것 |
|---|---|---|
| 애플리케이션 | 지정 객체 조회·변경, 자기 거래 관리 | 다른 세션 SQL, 설정 변경, 서버 종료 |
| 관측 | 허용된 대상의 상태·통계 | 원문 SQL·bind·민감 경로·다른 사용자의 숨긴 객체 |
| 운영 | 허용된 대상의 취소·작업·기동/종료 | 권한 부여, 원문 진단, 감사 정책 변경 |
| 설정 관리 | 허용 설정의 검증·변경 | 모든 데이터 조회, 보안 정책 우회 |
| 보안·감사 | 계정·권한·정책 또는 감사 조회 중 위임된 업무 | 감사 삭제·보존 축소와 일반 조회를 동일 권한으로 묶지 않음 |
| 지원 진단 | 승인된 대상·시간·예산의 수집 | 자격 증명·업무 데이터 전체 접근을 자동 부여하지 않음 |

권한 철회 후 실행 중 요청·오래된 prepared 객체·새 요청에 언제 적용하는지는 MS-08에서 확정합니다. 최소한 관리 동작은 실제 실행 시점에 대상과 권한을 다시 검증합니다. 권한 거절 오류가 객체 존재 여부나 비밀 설정 값을 우회 노출하지 않아야 합니다.

인증서 교체 절차는 새 인증서의 대상 이름·신뢰 체인·유효기간·키 접근 권한 검증 → 시험 client 연결 → 지원되는 reload 또는 restart → 새 연결의 인증 결과 확인 → 이전 자격 증명 폐기 조건 확인 순서로 제안합니다. 기존 연결에 적용되는 시점, client/server 양쪽 교체 순서, 실패 시 복귀 가능한 조합은 배포별로 명시합니다. 검증을 끄는 옵션을 정상 해결 절차로 제공하지 않습니다. 지원 TLS·암호화·key rotation의 구체 범위는 미정입니다. 관련 인수 계획: MA-11.

## 12 상태 조회와 성능 조사

### 공개 조회 영역

| 제안 영역 | 읽는 정보 |
|---|---|
| `information_schema` | 선언한 표준 subset의 객체·열·권한 metadata |
| `xadb_catalog` | XADB 객체·설정·기능·뷰와 열 설명 |
| `xadb_stats` | 현재 활동·자원·누적 통계 |
| `xadb_history` | 실제 수집·보존한 과거 관측 |
| `xadb_diag` | 별도 권한과 비용 제한이 있는 내부 진단 |

이 이름은 공개 명세 전 제안입니다. 최종 뷰의 열·타입·단위·NULL·갱신·권한은 참고서에서 확정합니다. 일반 운영 자동화는 build별로 바뀔 수 있는 내부 진단 표현에 의존하지 않습니다.

### 통계 읽기

대상 ID와 관측 시각을 먼저 확인합니다. 누적값은 시작·초기화 시점을, rate는 계산 구간을, percentile은 모집단·표본 수·기간을 함께 봅니다. 재시작 전후 counter를 단순히 빼지 않습니다.

수집 중단·표본 부족·권한 제한·미지원·보존 만료는 0이 아닙니다. 여러 live 뷰를 join한 값도 같은 순간의 snapshot이라고 보장되지 않을 수 있습니다. 파티션과 테이블 합계, 공유 메모리를 이중 합산하지 않습니다.

### 느린 요청 조사

1. 발생 시간·애플리케이션·업무 범위를 정하고 평소와 비교 가능한 구간을 선택합니다.
2. 비용이 큰 쿼리와 실제 요청을 구분합니다. 쿼리 요약이 특정 요청을 보존했다는 뜻은 아닙니다.
3. 실행·대기·자원·plan 정보를 관측 시각과 함께 확인합니다.
4. 관련 설정 변경·사건을 찾고 원인으로 확인된 사실과 후보를 구분합니다.
5. 조치의 대상·영향을 검토한 뒤 실행하고 같은 조건에서 결과를 비교합니다.

<!-- manual-example: EX-06 -->
**문법 제안·실행 미검증**

```sql
SELECT session_id, application_name, request_id, state, wait_kind, elapsed_ms
FROM xadb_stats.requests
WHERE state = 'waiting';
```

기본 plan 조회는 실행하지 않는 것으로 설계합니다. 실제 실행 통계를 얻는 기능은 읽기 쿼리도 자원을 사용하며 DML은 데이터를 바꿀 수 있습니다. 실행을 동반하는지 확인한 뒤 사용하십시오. 전체 TPS·p99·최대 용량의 제품 보장 수치는 아직 정해지지 않았습니다.

<a id="manual-observation"></a>
### 공개 뷰 사전의 필드 계약 제안

뷰마다 한 행의 단위, key의 유효 범위, 갱신 방식·최대 지연, 누적값 초기화, 권한·비용·상한을 문서화합니다. 업무 테이블의 SQL NULL과 관측할 수 없는 값을 구분하기 위해 관측 상태를 함께 제공합니다. 명칭·정확한 열 타입은 MS-04에서 확정합니다.

| 제안 뷰 | 한 행과 핵심 정보 | NULL·관측·권한 규칙 |
|---|---|---|
| `xadb_catalog.capabilities` | 기능 ID·제공 여부·지원 제약·build | 행이 없다고 지원으로 가정하지 않음; 권한 거절과 미지원 구분 |
| `xadb_catalog.settings` | 설정 정의 1개, 타입·단위·기본값·범위·적용 시점 | 비밀 값은 정의와 분리, 미정 기본값을 0으로 채우지 않음 |
| `xadb_stats.requests` | 실행 1개, instance/boot/session/request identity, 상태·대기·경과 시간 | 경과 시간은 nonnegative BIGINT ms 제안, 원문 접근은 별도 권한; 사라진 행은 성공 완료의 증거가 아님 |
| `xadb_stats.transactions` | 거래 1개, 시작 시각·현재 상태·자원·관련 요청 | 현재 활성 거래 조회와 과거 commit 결과 조회의 보존 범위는 별개 |
| `xadb_stats.memory` | 명세한 자원 owner·범위별 값·단위·관측 시각 | 공유 물리 메모리를 두 번 더하지 않음; 예약과 실사용 분리 |
| `xadb_history`의 관측 | 수집 구간·표본 수·집계 방식·보존 경계 | 미수집·만료·표본 부족을 0 대신 상태로 반환 |

관측 envelope에는 `observed_at`(시간대 포함), `boot_id`, `collection_status`와 필요하면 counter reset identity를 제안합니다. `collection_status`는 available/not_collected/insufficient_sample/expired/unsupported/redacted를 구분하는 안이며 권한상 존재 자체를 숨겨야 하는 대상은 반환하지 않습니다. 이런 이유 값을 다른 사용자 객체의 존재 확인 수단으로 노출하지 않습니다.

예를 들어 counter가 부팅 A에서 120, 부팅 B에서 5이면 -115라는 차이를 계산하지 않습니다. 같은 boot·reset 구간에서 120→150, 관측 간격 10초였다면 해당 정의의 rate는 3/초입니다. 표본이 없는 p99는 0ms가 아닙니다. 현재 요청이 사라졌어도 보존된 완료 사건이 없으면 원인을 단정할 수 없습니다. 관련 인수 계획: MA-12.

## 13 메시지 로그와 진단

### 메시지에서 먼저 볼 것

발생 시각·시간대, DB·인스턴스·부팅 구간, 메시지 코드, 심각도, 요청·트랜잭션·작업 ID, 영향 범위, 결과 확실성을 확인합니다. 코드는 사건 종류, event ID는 한 번의 발생, query ID는 정규화된 쿼리 형태, request ID는 실행 한 번을 뜻합니다.

심각도 제안은 TRACE·DEBUG·INFO·WARN·ERROR·FATAL입니다. ERROR를 봤다고 모든 트랜잭션이 실패한 것은 아닙니다. FATAL은 해당 인스턴스가 정상 서비스를 계속할 수 없는 상황에 한정합니다. 감사 기록은 일반 로그 수준을 낮춘다고 사라지는 대상이 아닙니다.

<!-- manual-example: EX-07 -->
**문법 제안·실행 미검증**

```text
ax logs --context lab-orders --level error --since 30m --format jsonl
```

### 검색 범위 확인

파일·컨테이너 stderr·시스템 journal·외부 수집기 중 실제 기록 경로와 보관 책임자를 확인합니다. 외부 전송 성공이 XADB에서 그 이력을 다시 검색할 수 있다는 뜻은 아닙니다. 검색 지원 여부·보존 구간·권한·공백을 확인하십시오.

기간과 용량 제한으로 일찍 삭제된 기록, sampling·억제·잘림·유실을 구분합니다. `--follow` 재접속이나 회전 때 중복·공백이 생길 수 있으며 실제 보장 범위가 별도로 표시돼야 합니다. 로그가 없다는 사실만으로 오류가 없었다고 판단하지 않습니다.

### 제한된 상세 진단

<!-- manual-example: EX-08 -->
**문법 제안·실행 미검증**

```text

```

대상·시간·용량·비용을 확인하고 수집을 시작합니다. 시간 인수만 있는 위 예제에도 유한한 용량·비용 예산의 확인이 필요하며, 정확한 옵션은 후속 명세에서 정합니다. 진단이 끝나면 자신이 추가한 수집만 해제합니다. 다른 운영자가 바꾼 기본 설정이나 다른 수집은 보존해야 합니다. 해제를 확인하지 못했다면 종료 완료로 표시하지 않습니다.

### 지원 자료 만들기

<!-- manual-example: EX-09 -->
**문법 제안·실행 미검증**

```text
ax support bundle --context lab-orders --incident E-72
```

대상과 시간 범위 선택 → 포함 정보와 민감 정보 확인 → 로컬 생성 → 포함·제외·실패 목록 확인 → 선택한 경로로 전달 순서입니다. 생성과 외부 업로드는 별개입니다. 기본 오류 사전과 묶음 열람은 인터넷·AI 연결 없이 가능해야 합니다.

기본 기록은 허용된 구조화 필드와 literal을 제거한 표현을 사용합니다. SQL 정규화 실패·parser 오류를 원문 기록으로 대체하지 않습니다. 원문 SQL 파일 히스토리는 명시적으로 선택하며 credential·분류 불가 문장은 제외합니다. 원문·bind·dump 수집을 선택해도 모든 비밀이 자동 제거된다고 가정하지 않습니다.

<a id="manual-diagnostics"></a>
### 오류 참고서와 수집 종료의 완료 조건

오류 항목에는 안정 코드, 사용자에게 드러나는 증상, 확정된 영향과 모르는 영향, 문장/거래 효과, 재시도 단위, 필요한 권한, 확인 순서, 관련 ID와 후속 자료를 붙입니다. 한국어 메시지 문구나 심각도만으로 프로그램 분기를 만들지 않습니다. 예를 들어 `XADB-SQL-UNIQUE`는 일반적으로 이번 문장의 효과 복원을 뜻하지만, 연결 단절 뒤 같은 거래 전체의 최종 결과까지 증명하지는 않습니다.

진단 수집에는 duration 외에도 최대 bytes·event rate·동시 수집 수·허용 대상이 필요합니다. 한도 도달, client 유실, 인스턴스 재시작, 정상 만료마다 실제 수집 상태·손실·잔존 파일을 보고해야 합니다. 수집 종료는 `수집 중단 확인`과 `결과 파일 완성`을 따로 확인합니다. 다른 수집이 같은 대상을 기록하고 있으면 자신의 종료 후에도 전체 로그 양이 유지될 수 있습니다.

지원 묶음의 제안 manifest에는 build·대상 identity·관측 시간 범위·수집 정책, 포함/제외/실패한 항목, 파일 크기·무결성 값·민감 정보 분류를 기록합니다. 빠진 파일을 빈 정상 파일로 채우지 않습니다. 묶음 생성은 외부 전송이 아니며 수신 대상·보존·접근 범위는 전달 절차에서 정합니다. 관련 인수 계획: MA-13, UX-12·13·16·24.

## 14 백업과 복구

**설계 기준 / 최소 관리 API는 DEV2 이후, 운영 기능·PITR은 후속 / 제품 시험 미실행.** 백업을 생성한 것과 복원 가능성을 검증한 것은 다릅니다.

### 백업 준비와 결과 확인

대상 DB identity, 포함 범위, 기준 시점, 필요한 복구 자료, 저장 위치, 용량·접근 권한, 검증 상태를 확인합니다. 백업 manifest와 필요한 파일의 완전성을 함께 관리합니다. 일부 파일만 복사한 자료를 유효한 백업으로 취급하지 않습니다.

백업 작업의 완료 응답 뒤에는 실제 복원 시험과 논리 데이터·제약 확인 결과를 따로 기록합니다. 백업을 만들었다는 이유로 현재 DB와 동일 시점의 데이터가 보존된다고 가정하지 않습니다.

### 복원 절차

1. 필요한 복구 시점과 백업·복구 자료의 지원 범위를 정합니다.
2. 목적지와 기존 DB의 충돌·덮어쓰기 영향을 확인합니다. 독립된 빈 환경에서의 복원을 우선 검증합니다.
3. 복원을 실행하고 단계·오류·결과 불명을 구분합니다.
4. 준비 상태와 실제 행·제약·업무 결과를 확인합니다.
5. 확인한 데이터 시점과 이후 손실 가능 범위를 명시한 뒤 업무 연결을 전환합니다.

### 재시작 복구와 보장 범위

같은 트랜잭션의 변경은 전체 반영 또는 미반영이어야 하며 부분 변경을 정상 결과로 받아들이지 않습니다. 성공 응답을 관측한 commit은 선언한 장애 모델 안에서 복구 후 보존돼야 합니다. 성공 응답이 없던 요청도 실제로는 영속 commit됐을 수 있습니다.

필수 영속 영역의 손상은 명시적 복구 오류일 수 있습니다. 손상 자료를 임의로 삭제하거나 메시지 로그만으로 정상화를 판정하지 않습니다. process 재시작 시험, 파일 오류 주입, 전원 장애 내구성 검증은 다른 범위입니다. 허용 데이터 손실량(RPO)과 복구 시간(RTO)은 기능·배포 환경별 검증 기준으로 정합니다.

<a id="manual-recovery"></a>
### 복구 목적별 필요한 자료

| 목적 | 필요한 범위와 완료 기준 | 아직 약속하지 않는 것 |
|---|---|---|
| 현재 build의 crash 재시작 | 유효 checkpoint·필요 WAL·참조 데이터 객체, 실제 recovery 후 ACK 보존·원자성 | process kill 시험만으로 전원 장애 내구성 보장 |
| DEV2 K5 기준점 복원 | committed cut C의 완전한 checkpoint closure를 빈 소유 환경에 복원, C의 논리 상태 확인 | 백업 뒤의 모든 commit까지 자동 복구 |
| 매체 유실 후 확장 복원 | 목표까지의 commit group·payload·모든 참조 COW 객체와 metadata | root만 기록한 WAL이 유실된 DISK page를 재생성한다는 가정 |
| 시점 복구(PITR) | 지원 범위의 완전한 commit group 경계와 실제 선택 시점 보고; 새 쓰기 전 새 timeline | group 내부의 임의 벽시계 시각이나 아직 없는 연속 아카이브 기능 |
| 논리 export/import | 대상 schema·값·제약·일관된 추출 시점과 재적재 검증 | 물리 DB·권한·운영 상태 전체의 동일 복구 |

checkpoint는 엔진의 복구 기준점이고 독립 보관 백업과 동일하지 않습니다. 같은 매체에만 있는 checkpoint가 매체 유실을 보호한다고 안내하지 않습니다. 백업의 closure는 manifest가 참조하는 모든 데이터·catalog·색인·복구 의존 자료의 완전한 묶음입니다. checksum 일치만으로 논리 데이터와 제약의 정확성까지 판정하지 않습니다.

**복원 실습의 제안 기대값:** 4장의 fixture를 포함하는 C의 백업을 완성한 뒤 원본에서 1001의 quantity=5를 commit했다고 가정합니다. C만 복원하면 quantity는 2입니다. 후속 commit까지 필요한 자료가 모두 있는 확장 복원을 선택하면 5이며, 2와 5를 섞은 부분 거래는 허용되지 않습니다. 실제 목표 시점과 복원 결과를 함께 보고합니다.

복원 중단 후 재개는 같은 backup identity·manifest·목적지 generation을 확인하는 기능으로 명세해야 합니다. 마지막 출력 줄만 보고 재개하지 않습니다. 완료되지 않은 목적지를 READY로 열지 않고, 필수 파일이 없으면 누락과 중단 단계를 보고합니다. 재개 지원이 없다면 실패 자료와 원본을 보존한 별도 빈 목적지에서 새 작업으로 수행합니다.

### 보존과 공간 부족 대응

WAL·checkpoint 파일은 나이만 보고 수동 삭제하지 않습니다. 복구, backup, replication/archive 등 소비자의 보존 책임과 pin을 확인합니다. 오래된 reader가 요구하는 자료와 RP가 요구하는 WAL이 항상 같은 것은 아닙니다. 관측에는 어떤 소비자가 어떤 기준점부터 보존을 요구하는지, 확보 가능한 공간·증가량·해소 조건이 필요합니다.

공간 부족이면 제한된 신규 작업·쓰기를 거절하고 원인을 설명하는 정책을 명세합니다. 필요한 자료를 먼저 지워 정상처럼 계속하는 방식은 허용하지 않습니다. backup 완료·archive 전달·RP 수신 ACK는 각자의 책임 인계 조건이 다르며, 복원 가능성과 소비자 재시작 가능성을 확인한 보존 정책으로 회수합니다. 수치와 우선순위는 MS-09에서 확정합니다. 관련 인수 계획: MA-14, MA-15.

## 15 복제와 장애 전환

**후속 기능 / topology·구문·수치 미정.** 복제는 백업과 별도 기능입니다. 잘못된 변경도 다른 노드에 전달될 수 있으므로 복제 구성이 복원 시험을 대신하지 않습니다.

복제 구성 전에 쓰기 노드와 대상 객체, 동기·비동기 모드, 초기 동기화, 충돌 정책, DDL·sequence 처리, 전환 조건과 권한을 정해야 합니다. 구체적인 지원 topology와 혼합 버전 운용은 별도 검증 범위를 따릅니다.

상태 조회에서는 연결됨, 수신 진행, 적용 진행, 관측 시각과 지연 단위를 구분합니다. 연결이 유지된다는 사실만으로 최신 데이터가 적용됐다고 판단하지 않습니다.

전환은 이전 쓰기 노드의 격리 조건 확인 → 새 노드의 적용·데이터 상태 확인 → 전환 작업 → 애플리케이션 재접속 → 업무 결과 확인 순서로 검토합니다. 결과를 확인하지 못하면 양쪽에 임의로 쓰기를 허용하지 않습니다. 자동 전환·failback·무중단 운용은 검증된 조합에서만 안내합니다.

<a id="manual-replication"></a>
### 복제 진행과 전환의 판정표

다음은 DEV8 기능 명세를 작성할 때 적용할 동작 기준입니다. 실제 topology·전환 명령·동기 모드의 ACK 조건은 아직 미정입니다.

| 관측·작업 | 확인할 계약 | 잘못된 완료 판정 |
|---|---|---|
| 초기 동기화 | 기준 snapshot과 이후 변경 stream의 연결점·schema epoch, 완료 시 데이터 비교 | 복사 행 개수만 같으면 동기화 완료 |
| 수신·적용 | 수신 위치, 영속 보존 위치, 적용 commit 위치와 각각의 단위·시각 | 연결됨 또는 전송됨을 적용 완료로 취급 |
| 로그 회수 | capture restart에 필요한 열린 거래·분석 상태의 영속 인계, 재시작 pin | 가장 멀리 읽은 위치만으로 원본 WAL 삭제 |
| 충돌 | 대상·키의 보호된 식별, 충돌 유형, 중단/해결 정책과 데이터 손실 영향 | 오류를 로그에만 남기고 양쪽 데이터 일치를 주장 |
| 계획 전환 | 새 쓰기 제한, 이전 writer 격리, 목표 적용점 확인, 승인된 연결 전환 | 두 노드의 쓰기를 동시에 열고 나중에 조정 |
| 비계획 전환 | 마지막 확인 위치와 유실 가능 범위, 격리 증거, 선택한 복구 정책 | 비동기 연결의 복구만으로 RPO=0 선언 |
| failback | 이전 노드 격리 유지, 차이 처리·재동기화, 재검증 후 역할 변경 | 오래된 노드를 단순 재시작해 writer로 복귀 |

전환 도중 대상이 바뀌거나 상태를 확인할 수 없으면 완료 불명으로 남기고 writer 격리를 유지합니다. 어떤 승인·조정 주체가 격리를 보장하는지 후속 HA 명세에 명시해야 합니다. 연결 failover는 거래 재실행과 다릅니다. 새 노드에 접속했더라도 옛 거래 결과·세션 옵션·prepared/cursor 수명을 다시 판단합니다. DDL·sequence·LOB·queue·다중 writer의 충돌 조합은 기능별 인수 범위를 별도로 정합니다. 관련 인수 계획: MA-16, MA-17.

<a id="section-16"></a>

## 16 데이터 이관과 버전 변경

### 기존 업무를 XADB로 옮기기

객체·타입·SQL·PSM·client·운영 작업 목록을 만든 뒤 각 항목의 XADB 대응, 변환 가능 여부, 제약, 독립 검증 결과를 기록합니다. 미지원 객체를 조용히 생략한 export/import는 이관 완료가 아닙니다.

1. source의 버전·설정·인코딩과 사용 기능을 조사합니다.
2. 객체·타입·SQL의 변환안을 검토하고 손실·지원 불가·수동 판단 항목을 분리합니다.
3. 논리 schema와 데이터를 이동하며 오류 행·부분 성공·재개 위치를 보존합니다.
4. NULL·빈 문자열·정밀도·binary·LOB·문자 값과 제약·업무 결과를 비교합니다.
5. 불일치 원인을 해결하고 선택 동기화의 변경 대상·충돌 정책을 확인합니다.
6. 전환 조건과 복귀 절차를 충족한 뒤 연결을 바꾸고 결과를 다시 확인합니다.

행 개수만 같거나 importer가 성공을 반환한 사실만으로 데이터 동등성을 판정하지 않습니다. 비교와 실제 동기화는 별도 행동입니다. 선택 동기화는 데이터를 변경하므로 미리보기·권한·변경 결과를 확인합니다.

<a id="manual-transfer"></a>
### 논리 내보내기·적재의 파일 계약과 재개

**후속 데이터 도구의 상세 제안.** export manifest에는 source identity·schema와 타입/단위·정렬/NULL 정책, 선택 대상·필터, 일관성 기준(snapshot 또는 대상별 시점), 인코딩, 파일 목록·크기·hash, 완료 상태를 기록합니다. 데이터가 계속 바뀌는 여러 테이블을 다른 시점에 읽었다면 DB 전체의 일관된 snapshot으로 표시하지 않습니다. LOB 별도 파일·권한·sequence·종속 객체의 포함 여부도 명시해야 합니다.

CSV profile에는 UTF-8, 헤더 유무, 열 순서, 구분자·인용·escape·개행, NULL 토큰·빈 값·문자열 NULL의 구분, binary 표현을 함께 고정합니다. 인용 여부를 잃은 일반 CSV parser가 NULL과 빈 값을 구분한다고 가정하지 않습니다. 손실 없는 profile이 없으면 타입 metadata를 포함한 형식을 선택합니다. 숫자 정밀도·시간대 변환이나 잘못된 인코딩을 자동 보정하는 옵션은 명시적으로 선택해야 합니다.

적재 전 대상 identity·schema·제약·인코딩·공간, append/replace의 영향, commit 단위, 오류에서 중단/계속, 동시 쓰기 허용 범위를 검증합니다. 기본 제안은 기존 데이터 자동 삭제 없음·오류에서 중단입니다. replace·제약 비활성화·복제 우회·비내구성 적재를 성능 옵션의 숨은 효과로 넣지 않습니다.

| 적재 결과 항목 | 의미 |
|---|---|
| 읽은/검사한 행 | 파일 처리 진척이며 DB 반영 수가 아님 |
| committed 행·chunk | 서버가 확정했다고 확인한 범위와 입력 식별 |
| 거절 행 | 원본 위치·오류·보호된 진단; 원문 저장 위치는 별도 접근 제한 |
| 미실행 범위 | 아직 보내지 않은 입력 |
| 결과 불명 범위 | 보냈으나 효과를 확인하지 못한 입력; 거절 행에 합산하지 않음 |
| resume 정보 | 입력 hash·manifest·대상 generation·변환 규칙·마지막 확정 chunk |

예를 들어 chunk 1(2행)을 commit한 뒤 chunk 2(2행)의 두 번째 행이 실패하고 chunk 전체 원자성을 선택했다면, 결과는 committed=2, chunk 2 미반영=2입니다. 마지막 오류 행만 고쳐 재시작하면 그 chunk의 첫 행이 누락될 수 있습니다. 반대로 chunk 2 응답만 유실됐다면 2행 모두 반영 또는 모두 미반영일 수 있어 결과 조회 없이 재적재하지 않습니다. 행별 계속 모드는 원자 chunk 모드와 다른 계약으로 결과를 표시합니다.

완료 확인은 행 수 외에도 안정된 업무 키로 값·NULL·빈 문자열·binary·정밀도, 누락·추가·중복 행, schema·제약·업무 결과를 비교합니다. hash 비교는 정의한 canonical 값과 구간이 같을 때 보조 증거로 쓰고 불일치 시 실제 차이를 조사합니다. 비교만 하는 작업은 쓰지 않으며 선택 동기화는 대상·generation·검토한 revision과 충돌 정책을 재확인한 별도 변경입니다. 관련 인수 계획: MA-18, MA-19.

### 사내 버전과 안정 릴리스 버전

사내 배포는 새 DB·fixture로 구축하며 이전 사내 DB·WAL·backup·client/API의 호환이나 변환을 요구하지 않습니다. 새 구축은 기존 경로를 자동 삭제·덮어쓰기한다는 뜻이 아닙니다.

최초 안정 릴리스부터는 같은 XADB major의 이전 안정 릴리스 버전을 새 버전이 처리하는 단방향 계약을 적용합니다. 이전 client·공개 SQL/오류 의미·설정·기계 출력·데이터·복구 자료에 관한 지원 범위를 배포 문서에서 확인합니다. 중간 서버를 모두 설치해야 하는 단계별 업그레이드를 필수로 삼지 않는 정책입니다.

새 client가 옛 server에서 동작하는 것, 옛 binary가 새 파일을 여는 것, 혼합 버전 복제·rolling upgrade·무손실 downgrade는 자동으로 보장되지 않습니다. 업그레이드 전 백업으로 돌아가면 그 이후 확정한 변경을 잃을 수 있습니다.

### 안정 릴리스 후 업그레이드의 완료 기준

업그레이드 대상은 사내 배포가 아닌 **이전 안정 릴리스 same-major 버전**입니다. source 버전·build·format·capability와 보존 fixture를 식별하고 새 엔진이 직접 읽거나 내부 변환 사슬을 적용할 수 있는지 확인합니다. 중간 서버 설치를 필수로 요구하지 않는 정책입니다.

변환의 기준 절차는 쓰기 중단·복구 원본 보존 → shadow generation 생성·재개 journal 기록 → 데이터·ACK·제약 검증 → durable manifest로 선택 → 새 엔진으로 재시작·쓰기·재복구 확인 → 회수 조건을 충족한 원본 정리입니다. 어느 장애 절단점에서도 완전한 old 또는 new generation을 선택해야 하며 둘을 섞지 않습니다. 구 binary의 지원하지 않는 새 형식 거절은 방어 동작이며 downgrade 지원이 아닙니다. 관련 인수 계획: MA-20.

| 성능·용량·배포 | 1·3·12·16장 | 검증 환경·한도·workload·버전별 차이 |

이 표는 세부 기능 명세와 인수 목록의 완성을 뜻하지 않습니다. 후속 장을 작성할 때 지원되지 않는 항목을 삭제하지 않고 도입 범위와 미정 사항을 추적합니다.

### 확장 기능의 구현 전 사용자 계약

아래는 누락되기 쉬운 후속 기능을 구현할 때 답해야 하는 사용자 질문과 최소 반례입니다. 새 문법·기본값을 동결한 표가 아니며 모두 미구현입니다. 정확한 요구 ID별 위치와 남은 상세는 [104개 추적표](manual-review.md#section-4)를 따릅니다.

| 추가 격리·savepoint·잠금 (R03) | snapshot 시점·이상 현상 허용 범위, savepoint rollback 자원 범위, 잠금 timeout | write skew·phantom·교착, 취소 뒤 거래 생존 여부 |

후속 참고서는 기능명 나열로 끝내지 않고 대표 정상 입력, 실패 입력, 실패 후 실제 상태, 필요한 동시성·복구·client 조합을 작성합니다. 기능 제품 요구의 overload·옵션·조합 상세는 계속 확장해야 하며 현재 104개 요구를 최종 leaf 목록으로 간주하지 않습니다.

## 19 참고 자료와 초안의 관리

이 초안의 XADB 동작은 [제품 기준선](../plans/phase1-product-baseline.md), [개발 단계](../plans/development-stages.md), [구현 계약](../contracts/implementation-contracts.md), [인터페이스 기획과 리뷰](interface-experience-plan.md), [기능 제품 요구](../plans/product-requirements.md), [복구 설계](../contracts/recovery-logging-design.md), [버전 정책](../policies/version-compatibility-policy.json)을 기준으로 합니다. 현재 구현 사실은 [DEV0 기록](../implementation/dev0-implementation.md)과 [DEV1 기록](../implementation/dev1-implementation.md)에서 범위를 확인합니다.


매뉴얼을 실행 가능한 버전별 안내로 발전시킬 때는 각 항목의 **명세 확정 → 실제 구현 → 독립 기대값과 예제 실행 → 배포 지원 범위 확인**을 연결합니다. 먼저 구현할 기능의 명세부터 구체화하며 전체 매뉴얼의 완성을 하위 계층 개발의 선행 조건으로 두지 않습니다.

초기 SQL의 타입·구문·샘플 생성·실패 예제는 [별도 명세 초안](sql-language-draft.md)에서 구체화했습니다. 이 선택을 검토하고, 설치 명령·포트·지원 환경, CLI 옵션·종료 코드, 공개 뷰의 열, 설정별 기본값·출처·적용 범위, 권한표, SQLSTATE 매핑, 결과 조회·보존 기한을 해당 기능 구현 전에 확정합니다. 현재의 개념·업무 절차와 구체적인 SQL 예제는 그 판단의 기준으로 사용할 수 있습니다.
