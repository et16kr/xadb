# XADB 사용자·운영 인터페이스 경험 기획

2026-10-18 · **제품 경험 제안 / 미구현 / 사용자 평가·제품 인수 시험 미실행**


**최종 모습은 “현재 상태를 이해하고, 변경의 영향을 예측하며, 문제가 생기면 같은 맥락에서 해결하는 DBMS”다.** 설정 파일, 시스템 뷰, 로그 파일, SQL 도구를 각각 잘 만드는 데서 멈추지 않고, 같은 대상·이름·시간·식별자로 연결한다. DBA에게는 깊이 있는 SQL 접근을, 개발자에게는 이해할 수 있는 오류를, 운영자에게는 빠른 판단을, 자동화에는 예측 가능한 결과를 제공한다.


이 문서는 화면·명령·정보 구성·행동과 완료 기준을 정하는 기획이다. 모듈, Rust 타입, wire encoding, 저장 구조, 수집 파이프라인은 정하지 않는다. 예시 이름·명령·수치·코드는 제안이며 설치된 기능이나 확정 공개 명세가 아니다. 기존 DEV0의 `xadbtest` 구현과도 구별한다.

**리뷰 반영:** 응답 유실 때의 작업 식별, 임시 진단 종료와 동시 변경, 기계 출력의 완료 판정, 설정 출처·만료, 외부 로그 검색 범위, SQL 기록의 민감 정보 경계를 보완했다. 수정 내용과 남은 명세 작업은 17절에 기록한다. 기획 검토와 제품 동작 검증은 별개다.

## 1. 권고하는 최종 제품 모습

| 결정 | 사용자가 얻는 경험 |
|---|---|
| 하나의 제품 언어 | SQL·CLI·화면·매뉴얼에서 동일한 설정명, 객체명, 상태, 오류 코드 사용 |
| `xadb`라는 한 명령행 입구 | `xadb sql`, `xadb config`, `xadb activity`, `xadb logs`, `xadb doctor`에서 일상 업무 완료 |
| 설명 가능한 설정 | 현재 값, 저장 값, 실제 적용 출처, 적용 대상, 재시작 필요성, 변경 이력을 함께 확인 |
| 지원되는 공개 운영 뷰 | 일상 업무를 내부 X$ 상당의 구조에 의존하지 않고 SQL로 완수 |
| 사건 중심 메시지 로그 | 모듈별 파일을 찾기 전에 문제, 시간, 요청, 세션, 객체로 검색 |
| 동일 기능의 관리 화면 | 개요 → 활동/쿼리 → 객체 → 설정 → 이벤트 → 작업으로 이동하며 조사 맥락 유지 |
| 근거가 있는 조치 | 관측 사실·가능 원인·미확인 부분을 구분하고, 영향과 결과를 확인한 뒤 작업 완료 |

제품의 기본 제공 범위에 공개 운영 뷰, 설정 설명, 오류 사전, 메시지 로그 조회, 기본 쿼리 통계, 진단 묶음 생성을 포함하는 것을 권고한다. Fleet 통합·장기 중앙 보관·조직별 고급 분석은 확장할 수 있지만 단일 DB의 기본 장애 대응이 별도 유료 도구나 외부 AI 서비스에 의존해서는 안 된다.

세련됨은 장식보다 **예측 가능성, 발견 가능성, 설명의 정확성, 익숙한 작업의 짧은 경로**에서 나온다. “설정이 저장됐음”과 “이미 적용됐음”, “요청을 받음”과 “작업을 끝냄”, “없음”과 “볼 수 없음”을 혼동하지 않는 것이 디자인의 첫 조건이다.

## 4. 사용자와 정보 구조

| 사용자 | 첫 질문 | 기본 진입점 | 끝났다고 느끼는 순간 |
|---|---|---|---|
| 애플리케이션 개발자 | 연결됐나, 왜 실패했나, 다시 실행해도 되나 | `xadb sql`, driver 오류, 쿼리 상세 | 결과·거래 상태·다음 행동이 명확함 |
| DBA | 무엇이 느린가, 무엇을 바꾸면 되나 | 활동·쿼리·설정, 공개 뷰 | 근거 있는 변경 후 효과를 확인함 |
| 당직 운영자 | 서비스 영향이 있나, 지금 할 일이 뭔가 | 개요·이벤트·작업 | 영향 범위와 담당·조치 상태를 인계함 |
| 플랫폼 자동화 담당 | 반복 실행과 업그레이드가 안전한가 | CLI 구조화 출력·관리 인터페이스 | 결과를 분기하고 실패 지점부터 이어감 |
| 지원 엔지니어 | 정확히 어떤 환경에서 무엇이 관측됐나 | 사건 상세·진단 묶음·고급 진단 | 부족한 증거와 다음 수집 범위를 식별함 |

최상위 메뉴는 **개요 / 활동·쿼리 / 데이터·객체 / 설정 / 이벤트·로그 / 작업 / 접근 관리**로 제안한다. 도움말은 별도 문서 검색 외에 각 화면·명령에 붙는다. 인스턴스가 하나여도 환경·DB·인스턴스·역할·접속 사용자·관측 시각을 공통 머리말로 보여 준다. 여러 DB·노드의 실제 지원은 capability에 따라 노출하며 초기 단일 인스턴스에 가상의 cluster 기능을 표시하지 않는다.

모든 상세 화면은 **요약 → 근거 → 관련 항목 → 가능한 행동** 순서다. 초보자와 전문가를 별개 제품으로 나누지 않고, 같은 화면에서 상세 열·SQL·원시 필드를 펼친다. 검색은 설정·객체·오류·사건·도움말을 대상으로 하며 이름뿐 아니라 “재시작 필요”, “메모리”, “느린 쿼리” 같은 목적어로도 찾는다.

## 5. Property를 ‘설명 가능한 설정’으로 바꾼다

### 5.1 이름과 발견


기본 설정 화면은 연결·접근, 자원, 쿼리, 저장, 메시지·관측, 가용성으로 구성한다. **기본 / 고급 / 지원용** 수준을 표시하고 고급도 검색 가능하게 한다. “숨김 설정을 알아야 정상 운영”하는 상황은 공개 설정 부족으로 취급한다. 첫 설치는 필수 입력 5개 이하를 목표로 하되 인증·보안 선택을 몰래 생략해 숫자를 맞추지 않는다.

### 5.2 모든 설정에 붙는 설명 카드

| 사용자의 질문 | 반드시 보이는 정보 |
|---|---|
| 무엇을 바꾸나 | 한 문장 목적, 영향을 받는 업무, 관련 설정 |
| 어떤 값을 넣나 | 타입·단위·허용 범위·enum, 0/미설정/자동의 정확한 의미 |
| 지금 얼마인가 | 이 대상에서의 유효 값과 사람이 읽는 표시 값 |
| 왜 이 값인가 | 적용 출처, 덮어쓴 값, 권한이 허용하면 파일·항목 위치 |
| 저장도 됐나 | 저장된 희망 값, 아직 검증만 한 값, 적용 대기 값 구분 |
| 언제 달라지나 | 즉시 / 새 세션 / 명시적 재적용 / 재시작 / 생성 시 고정 |
| 누가 영향받나 | 인스턴스·DB·역할·세션 중 실제 지원 범위, 기존 세션 영향 |
| 무엇을 잃나 | 메모리·지연·처리량·메시지 양·재시작 등 알려진 trade-off |
| 되돌릴 수 있나 | 이전 값, 재변경 가능 여부, 기존 작업에 남는 효과 |
| 누가 바꿨나 | 변경자·시각·이유·변경 ID·변경 전후 상태 |

용량은 `MiB/GiB`, 기간은 `ms/s/min` 등 단위를 입력·표시하며 기계 출력에는 정규화 값과 단위를 함께 준다. `unlimited`, `auto`, `unset`을 의미가 서로 다른 이름으로 표시한다. default가 환경에 따라 계산되면 계산에 사용한 자원 한도와 기준 버전을 보여 준다. 새 버전에서 기본값이 달라지면 업그레이드 미리보기에 영향을 드러내며 기존 계약 보존 여부를 버전 정책으로 판단한다.

### 5.3 출처와 설정 소유권

공개 설정마다 허용한 범위만 적용한다. 일반적인 값 결정 순서는 **기본값 → 인스턴스 정책 → DB 기본값 → 역할 기본값 → 세션 값 → 명시적 실행 한정 값**이다. 상위 자원·보안 한도는 하위 값으로 완화할 수 없으며 “한도에 의해 제한됨”으로 설명한다. 이 순서는 경험 모델 제안이고 아직 없는 DB별/역할별 override를 지원했다고 주장하지 않는다.

인스턴스의 영속 설정은 **파일 관리 또는 제품 내 관리 중 하나를 소유자로 선택**한다. 파일 관리 모드에서 화면 변경은 검증과 수정안 내보내기까지 제공한다. 제품 내 관리 모드에서는 동일 변경을 CLI·SQL 관리 동작·화면에서 수행할 수 있다. 서로 다른 설정 저장소를 조용히 번갈아 덮어쓰지 않는다. 파일·환경변수·시작 옵션을 통한 배포 입력도 적용 출처로 보이며, 임시 override는 허용된 항목에만 만료 시각과 함께 표시한다.

범위 간 우선순위와 **같은 범위 안의 입력 출처 우선순위**는 별개다. 같은 인스턴스 범위에서는 선택한 영속 소유자의 값 위에 허용된 환경변수, 시작 옵션 순으로 적용하는 것을 기본안으로 한다. 지원하지 않는 입력 경로는 명시적으로 거절하며 상위 한도·보안 정책을 하위 값이나 임시 입력으로 우회하지 못한다. 정책 자체의 변경에는 해당 관리 권한과 검증을 적용한다. 상위 입력에 가려진 영속 값을 저장했을 때는 현재 값과 다음 시작 예상 값을 별도로 보여 준다. 다음 시작의 환경변수·옵션을 확인할 수 없으면 예상 값은 미확정으로 남긴다. 소유자 전환은 양쪽 값과 출처를 비교하는 명시적 변경이며 자동 fallback이 아니다.

만료 시 원복 가능한 임시 override는 해당 적용 범위와 해제 동작을 지원하는 설정에만 허용한다. 재시작·생성 시 고정 항목에는 즉시 원복되는 TTL을 제안하지 않는다. 임시 값이 끝나면 **그때의 영속 값과 남은 유효 override**로 다시 계산하고, 시작할 때 저장한 과거 값을 덮어쓰지 않는다. 자동 재시작·세션 종료가 필요한 해제는 별도 작업으로 표시한다.

### 5.4 변경 흐름과 상태

**선택 → 변경안 검증 → 영향 미리보기 → 적용 → 적용 결과 확인 → 변화 비교**가 기본 흐름이다. 읽기와 단순 조회에는 확인 대화상자를 넣지 않는다. 재시작·접속 차단·데이터 영향이 있는 동작은 대상과 효과를 구체적으로 보여 준다. 자동화는 대화형 확인 대신 대상·변경안·조건을 명시한다.

변경안은 `검증 오류 / 적용 가능 / 새 세션부터 / 재시작 대기 / 충돌 / 적용 실패`를 구분한다. 검토 후 다른 운영자가 설정을 바꿨다면 오래된 변경안을 그대로 덮어쓰지 않고 차이를 다시 제시한다. 여러 설정 묶음은 사전 검증에 실패하면 시작하지 않으며, 실행 중 일부만 적용됐다면 항목별 결과와 남은 조치를 보여 준다. 실제 보장 없이 전체 원자 적용이나 자동 원복을 약속하지 않는다.

변경안에는 대상 DB·인스턴스·객체의 identity/generation, 검토한 설정 revision과 유효기간을 연결한다. 실행 시점에도 대상·권한·관련 선행 조건을 다시 확인한다. context의 주소 변경이나 같은 이름의 객체 재생성은 기존 승인의 승계가 아니다. 오래된 세션·요청의 cancel도 같은 규칙을 적용한다. 미리보기는 자원 예약이나 실행 성공 보증으로 표시하지 않는다.

```text
설정 변경안 C-41                         대상: prod/orders · db-a
memory.limit      현재 8 GiB → 저장할 값 12 GiB
적용 시점         재시작 후              영향: DB 접속 일시 중단
현재 서버         계속 8 GiB 사용         기존 거래: 변경 없음
검증              유효 / 호스트 여유는 별도 재확인 필요
선택              [저장하고 재시작 대기로 두기] [변경안 내보내기]

결과              저장됨 · 아직 적용되지 않음
후속              작업에서 재시작 예약 또는 별도 실행
```

위 수치와 적용 방식은 설명용 가정이다. 모든 memory 설정이 반드시 재시작을 요구한다는 명세가 아니다. 재시작이 필요한 항목에 대해 “변경 성공” 한 줄만 출력하는 경험을 금지하는 예시다.

## 6. V$/X$를 대신할 공개 조회 경험

### 6.1 네 가지 역할을 구분한다

| 영역 제안 | 역할 | 사용자에게 하는 약속 |
|---|---|---|
| `information_schema` | 표준 객체·열·권한 metadata | 선언한 표준 subset과 일반 도구 연동 |
| `xadb_catalog` | XADB 객체·설정·기능·뷰 설명 | 문서화된 공개 SQL 계약, 이름·타입·의미 유지 |
| `xadb_stats` / `xadb_history` | 현재 상태·통계 / 보존된 관측 이력 | 갱신·집계·보존·권한·결측 의미를 공개 |
| `xadb_diag` | 지원·엔진 전문가용 내부 진단 | 별도 권한·비용 안내·build 식별, 일상 모니터링 의존 금지 |


공개하지 않은 내부 진단 표현은 build에 따라 달라질 수 있다. 수집물에는 정확한 build와 해석에 필요한 버전을 기록한다. 외부에 지원을 약속한 진단 명령·묶음 형식은 별도의 공개 계약이므로 내부 X$ 상당의 예외를 핑계로 깨뜨리지 않는다.

### 6.2 ‘테이블 목록’보다 먼저 준비할 질문

아래는 최종 공개 정보의 최소 목록이며 실제 DDL이나 확정 컬럼 명세가 아니다. `xadb_stats.*`의 이름만 만들고 값을 채우지 못한 기능을 제공된 것으로 세지 않는다.

| 업무 질문 | 제안 공개 정보 | 연결되는 다음 조사 |
|---|---|---|
| 지금 접속해도 되나 | `instances`, `health`, `capabilities` | 준비 상태·실패 이유·최근 사건 |
| 설정이 왜 이 값인가 | `settings`, `setting_values`, `setting_changes` | 적용 출처·대기 변경·영향 |
| 어떤 뷰와 열이 있나 | `views`, `columns`, `metrics` 사전 | 단위·권한·비용·갱신 의미 |
| 누가 무엇을 실행하나 | `sessions`, `requests`, `transactions` | 요청·SQL·대기·메시지 |
| 누구 때문에 기다리나 | `waits`, `blocking` | 관측된 의존 관계·기간·해소 여부 |
| 어떤 SQL이 비용을 쓰나 | `query_stats`, `plans` | 빈도·총비용·분포·plan 변화 |
| 메모리는 어디로 가나 | `memory`, `resource_limits` | 사용자 데이터·buffer·쿼리·예약·여유 |
| 디스크·I/O는 어떤가 | `storage`, `io` | 객체·영역·포화·실패 |
| 이 테이블은 어떻게 놓였나 | `tables`, `partitions`, `indexes` | DISK 배치·global 범위·상태 |
| 요청이 몰리나 | `admission`, `connections` | 대기·거절·한도·포화 |
| 복제 상태는 어떤가 | `replication` | 수신/적용 지연·관측 시각·전환 조건 |
| 백업·재시작은 어디까지 됐나 | `operations`, `backups` | 단계·진척·검증 여부·취소 가능성 |
| 메시지가 빠지거나 쌓이나 | `logging_status` | 대상 sink·손실/억제·공백·남은 용량 |
| 어제와 무엇이 달라졌나 | 보존된 query/resource 요약·변경/사건 이력 | 시간 구간 비교·수집 범위 |

### 6.3 통계의 의미까지 인터페이스다

각 조회는 대상 ID·관측 시각·수집 상태를 알 수 있어야 한다. 누적값에는 시작/초기화 시점, rate에는 구간, 표본에는 표본율과 개수, percentile에는 계산 구간과 모집단이 필요하다. 재시작 전후 counter를 빼서 음수 처리량을 만들지 않는다. 수집 중단·권한 없음·기능 미지원·표본 부족·보존 만료를 0으로 표시하지 않는다.

여러 live 뷰를 join했다고 같은 순간의 일관된 snapshot이 되는 것은 아니다. 뷰 사전에서 보장 범위를 설명하고 조사 묶음에는 관측 시간 범위를 표시한다. 객체·세션 ID의 재사용은 generation/instance identity로 구분한다. 논리 테이블 크기와 파티션 합계, 메모리의 공유 영역을 중복 합산하지 않도록 측정 정의를 제공한다.

현재값은 `xadb_stats`, 과거값은 `xadb_history`에서 구분한다. 과거 수집을 켜기 전 시간까지 복원해 보여 주지 않는다. 수집을 비활성화했거나 아직 지원하지 않으면 이유와 활성화 비용을 보여 준다. 공개 뷰의 고비용 조회는 비용 등급과 제한을 설명하고 기본 개요는 상시 사용에 적합해야 한다.

```sql
-- 최종 경험의 예시. XADB에 아직 존재하는 SQL/view가 아니다.
SELECT session_id, application_name, request_id, state, wait_kind, elapsed_ms
FROM xadb_stats.requests
WHERE state = 'waiting';
```

같은 결과에서 `request_id`를 선택하면 로그, SQL, 관련 객체, 당시 설정으로 이동한다. 기본 DBA 업무에 X$ 상당의 내부 구조 직접 조회가 필요하다면 공개 정보 목록을 보완해야 한다.

## 7. Message logging: 읽는 로그에서 해결하는 로그로

### 7.1 분류와 심각도는 서로 다른 축이다

| 메시지 종류 | 담는 것 | 기본 경험 |
|---|---|---|
| 운영 이벤트 | 시작·정지·준비 상태·설정 변경·자원 위험·작업 결과 | 상시, 사람이 이해하는 사건 목록 |
| 오류·경고 | 요청 실패·서비스 이상·운영 주의 | 안정된 코드와 영향, 관련 사건으로 연결 |
| 쿼리 진단 | 느린 요청·plan 변화·지연 분해 | 정규화된 쿼리 ID 중심, 원문·값은 별도 권한 |
| 감사 | 인증·권한·관리 동작, 정책상 필요한 접근 | 운영 메시지와 보존·권한·실패 정책을 분리 |
| 상세 trace | 특정 요청·세션·기능의 상세 상태 | 대상·시간·용량을 제한하고 자동 종료 |

외부 공개 심각도는 `TRACE / DEBUG / INFO / WARN / ERROR / FATAL`을 제안한다. `ERROR`는 어떤 작업이 실패했는지 scope와 함께 읽는다. `FATAL`은 해당 서버 인스턴스가 정상 서비스를 계속할 수 없는 상황으로 한정한다. 느린 쿼리는 서비스 오류와 같지 않으며, 감사 기록은 severity를 낮췄다고 사라지는 대상이 아니다. 운영자가 알아야 할 상태 변화는 INFO 수준에서도 남도록 한다.

`logging.level`은 메시지 양을 조절하는 기본값이고, 진단의 대상·범주 필터와 보존 정책은 별도로 보인다. `logging.level=debug` 하나로 모든 요청의 bind 값이 수집되는 식의 결합은 피한다. 내부 module 이름은 상세 분류로 남기되 사용자는 “접속”, “쿼리”, “설정”, “저장”, “복제”로 찾을 수 있어야 한다.

### 7.2 모든 중요한 사건이 답해야 하는 질문

메시지에는 **무슨 일이 있었나 / 어디에 영향이 있나 / 지금 결과는 무엇인가 / 다음 확인은 무엇인가**가 들어간다. 기계와 사람을 위해 동일 사건의 구조화 표현과 읽기 좋은 표현을 제공한다.

| 정보 | 목적 |
|---|---|
| 사건 ID와 발생 시각·UTC offset | 한 번 발생한 사건 식별, 타 시스템과 시간 대조 |
| 안정된 메시지 코드와 severity·분류 | 번역·문구 수정에도 검색과 자동화 유지 |
| DB·인스턴스·부팅 구간 | 다른 서버나 재시작 전 자료와 혼동 방지 |
| 관련 request/session/transaction/object/operation ID | 실제로 있는 연관만 연결, 없는 값은 만들지 않음 |
| 결과·영향 범위·확실성 | 요청 실패와 거래 전체 실패, 결과 불명을 구분 |
| 사실·권장 확인·도움말 참조 | 원인 단정 없이 행동 가능한 설명 |
| 수집 상태 | 반복 억제·sampling·잘림·누락 여부와 개수 |

코드는 사건의 **종류**, 사건 ID는 **발생 한 번**, query ID는 **정규화된 쿼리 형태**, request ID는 **실행 한 번**이다. 이 네 가지를 같은 ID처럼 사용하지 않는다. 민감한 SQL 원문·bind·credential은 기본 메시지, 히스토리, 지원 묶음에 남기지 않는다. 조회 권한이 없는 객체명이나 다른 사용자의 SQL도 오류·로그 경유로 노출하지 않는다.

기본 쿼리 진단은 허용된 구조화 필드와 literal을 제거한 표현만 사용한다. 정규화·민감 정보 분류에 실패한 SQL을 원문으로 대체하지 않으며, parser 오류의 주변 문자열·주석·오류 detail에도 같은 기준을 적용한다. 원문 SQL·bind·dump의 선택 수집은 별도 권한·대상·기간·보존 범위로 제한하고 credential은 그 선택으로 허용하지 않는다. 원시 자료에서 모든 비밀을 자동 제거할 수 있다고 보증하지 않으며, 검증할 수 없는 자료는 기본 지원 묶음에서 제외하고 제외 사유를 기록한다.

```text
14:32:10.421 +09:00  ERROR  XADB-QUERY-TIMEOUT       event E-72
orders / db-a       request R-912                 session S-44
요청이 제한 시간 5 s를 초과했습니다.
관측: 실행 1.2 s, 대기 3.8 s. 대기 상대의 상세 정보는 권한상 숨겨짐.
효과: 이번 문장은 취소되어 되돌려짐. 이전 성공 문장은 현재 거래에 남아 있음.
다음 확인: 요청 상세 보기 / 이 세션의 query.timeout 출처 확인
```

이 예시의 수치·코드·상태는 가상이며 해당 효과가 확인된 경우만 표시한다. **취소 요청 전송**만 확인됐다면 “취소 완료”라고 쓰지 않는다. 결과를 확인할 수 없으면 그 상태를 유지하며 임의 재실행을 권하지 않는다. 오류가 발생했다는 이유만으로 모든 statement가 서버 ERROR 로그에 무제한 반복되게 하지 않는다.

### 7.3 저장·검색·보존·전달

기본 사용자는 `xadb logs`에서 시간·심각도·코드·요청·세션·객체로 검색한다. `--follow`는 회전된 파일까지 이어 보되 연결 중단이나 누락 구간을 명시한다. 사람이 읽는 기본 출력과 versioned JSON Lines 출력을 제공한다. 다중 행 stack/SQL 설명은 하나의 사건에 속하며 별개 사건처럼 검색 결과를 오염시키지 않는다.

설치 프로파일은 **서버 파일 관리**, **컨테이너 stderr**, **시스템 journal/외부 수집 연계** 중 실제 경로를 명시한다. 기본값은 선택한 경로 하나가 보관 책임을 갖도록 한다. 중앙 수집기로 보냈다고 로컬과 중앙의 보관 기간이 같다고 가정하지 않는다. 화면에는 저장 위치·현재 sink·마지막 전달·보존 시작 시각·이용 가능한 검색 범위를 표시한다. 설치 장소와 무관하게 메시지와 검색 조건의 의미는 동일하되, **전송 가능한 경로와 다시 검색 가능한 경로는 구분**한다.

stderr 전송만 하거나 외부 검색 연계가 없으면 `xadb logs`가 외부 과거 기록을 읽을 수 있다고 약속하지 않는다. 조회 경로마다 지원 여부·권한·실제 보존 구간·필터·이어보기 가능 여부를 제공한다. 검색할 수 없는 구간은 0건이 아닌 조회 불가로 반환한다. 기본 로컬 상태·초기 진단 경로는 유지하되 그 범위를 전체 이력처럼 표시하지 않는다. 회전·재접속 때의 이어보기 위치는 instance/boot와 연결하고, 만료·중복·공백을 드러낸다. 여러 sink나 서버 사이의 전역 순서·무중복 전달은 별도 보장 없이는 주장하지 않는다.

파일 보관에는 기간과 총량 상한, 회전·압축·삭제 시점, 확보 용량을 함께 설정한다. “7일 보관”만 표시하고 용량 때문에 실제 2시간만 남기는 것을 허용하지 않는다. 상한으로 조기 삭제되면 실제 남은 범위를 보여 준다. 기본 운영 이벤트·쿼리 진단·지원 trace·감사에 각각 다른 예산을 줄 수 있다.

과부하에서는 상세 trace와 반복 메시지의 억제·누락 개수, 최초/최종 발생을 표시한다. 불변식은 **조용한 유실과 거짓 무오류 상태를 만들지 않는 것**이지 장애 시 모든 메시지의 무손실을 약속하는 것이 아니다. 비정상 종료로 잃을 수 있는 구간도 문서화한다. 일반 메시지 sink 장애로 무한히 업무를 정지시키지 않으며, 상태 조회·로컬 fallback 등 다른 경로에서 진단 불능을 드러낸다.

감사는 별도 정책이다. 기본 감사 사건은 sampling하지 않으며, 필수 감사 저장 실패 시 보호 대상 관리 동작을 시작 전에 거절하는 것을 기본안으로 한다. 이미 수행된 동작을 미실행이라고 거짓 보고하지 않는다. 업무 접근 감사의 fail-closed 범위는 적용 정책과 사용자 영향이 보이는 설정으로 다룬다. 중앙 수신 성공·로컬 기록·법적 보존 충족을 하나의 “저장 성공”으로 뭉개지 않는다.

시작 전 저장 가능 확인만으로 실행 후 결과 기록까지 보장하지 않는다. 보호 동작마다 정책이 요구하는 시작 전 기록 조건과 결과 기록 조건을 명시한다. 실행 도중 감사 경로가 실패하면 **동작 결과와 감사 기록 상태를 따로** 반환하며, 이미 확인된 효과를 rollback 또는 미실행으로 바꾸지 않는다. 효과 자체를 확인하지 못하면 결과 불명을 유지한다. 감사 실패의 해결을 위해 같은 변경을 자동 재실행하지 않는다.

### 7.4 상세 진단과 지원 인계

```text
ax diagnose capture --context prod-orders --request R-912 --duration 60s
ax logs --context prod-orders --request R-912 --since 15m
ax support bundle --context prod-orders --incident E-72
```

모두 미구현 명령 예시다. 진단 시작 전 대상, 수집 내용, 최대 시간·용량, 예상 비용을 보여 준다. 진단은 소유 ID와 만료 조건이 있는 임시 수집으로 관리한다. 종료 시 **자신이 추가한 수집만 해제**하고, 그 사이 운영자가 바꾼 기본 설정과 다른 활성 진단은 보존한다. 중첩 수집의 합산 예산·유효 수준을 표시하며, 하나가 종료됐다고 다른 수집도 꺼졌다고 보고하지 않는다. client 연결이 끊겨도 서버 측 한도로 종료하며 재시작 후 자동 재개를 기본값으로 하지 않는다. 해제를 확인하지 못하면 종료 완료가 아닌 미확인 상태를 표시한다.

지원 묶음은 코드·버전·허용된 설정 필드·관련 메시지·통계·수집 공백을 포함한다. 원문 SQL이나 dump는 별도 선택과 내용을 확인하는 과정이 필요하며 7.2절의 수집 제한을 따른다. 생성 후 포함 목록과 제외·실패 목록을 보여 주며 업로드는 독립 동작이다. 외부 접속이 없는 설치에서도 오류 사전과 묶음 열람이 가능해야 한다.

운영 DB가 준비되지 않았거나 SQL 접속이 실패한 경우에도 같은 서버 identity로 로컬 상태·초기 메시지·설정 오류를 읽는 경로를 제공한다. 이 경로도 OS 권한을 우회하지 않으며 “접속 실패”를 “DB 없음”으로 해석하지 않는다.

## 8. CLI: 익숙하면서도 자동화에 정확한 도구

### 8.1 명령 체계

| 입구 제안 | 수행 업무 |
|---|---|
| `xadb context` / `xadb connect` | 환경·접속 대상·인증·연결 진단 |
| `xadb sql` | 대화형 SQL, 파일 실행, 결과 내보내기 |
| `xadb status` / `xadb doctor` | 서비스 상태, 설치·접속·설정·관측 경로 확인 |
| `xadb config` | 찾기·설명·비교·검증·변경·이력 |
| `xadb activity` / `xadb query` | 현재 활동, 쿼리 통계·plan·대기 조사 |
| `xadb object` | 객체 정의·크기·배치·의존 관계 |
| `xadb data` / `xadb migration` | 논리 import/export·객체 변환 계획·데이터 비교·검증 |
| `xadb logs` / `xadb error` | 메시지 검색·따라보기·오류 설명 |
| `xadb operation` | 긴 작업 조회·대기·허용된 취소 |
| `xadb backup` / `xadb restore` / `xadb replication` | 해당 기능의 준비·실행·결과 확인 |
| `xadb diagnose` / `xadb support` | 제한된 수집과 인계 |

명령은 `자원 + 동작` 형태와 동일한 `--context`, `--format`, `--timeout` 등의 관례를 공유한다. `--help`는 예제와 부작용·권한·가능한 결과를 포함한다. 실제 DEV0 `xadbtest`는 개발 검증 도구로 유지한다. 종합 보고서의 `xadb test/reproduce`나 `axctl`이라는 기존 설계 표기는 사용자 명령 브랜드 확정 때 정리할 후보이며, 이번에 기존 하네스 명령·exit code를 변경하지 않는다.

### 8.2 SQL을 매일 쓰는 경험

대화형 프롬프트는 **환경 / DB / 사용자 / 읽기·쓰기 권한 / autocommit / 거래 상태**를 드러낸다. 색은 보조이고 텍스트만으로도 구분한다. 다중 행 편집·완성·검색·히스토리·객체 설명·쿼리 결과 가로/세로 표시·파일 실행·CSV/JSON 내보내기가 기본이다. 한글·넓은 문자·NULL·빈 문자열·큰 정수·binary·시간대 표현이 일관돼야 한다.

```text
prod / orders / app_reader  [read-only] [autocommit:on] [txn:idle]>
\help          \tables          \describe sales.orders
\settings      \activity        \timing on
```

메타 명령 철자는 제안이다. 화면에 나타나는 `NULL`을 문자열 "NULL"이나 빈 문자열과 구분해 내보낸다. 대량 결과는 진행·중단·잘림 여부를 알리고 메모리를 무한 사용하지 않는 경험을 제공한다. 붙여넣은 여러 문장 수, 적용 대상, 출력 생략을 표시한다. 기본 명령 회상은 세션 메모리 안에서 제공하고, 원문 SQL의 파일 히스토리는 명시적으로 선택해야 한다. 파일 기록을 선택해도 credential·비밀번호 변경문·분류 불가 문장은 기록하지 않는다. 일반 SQL literal도 업무 비밀일 수 있으므로 비밀번호 명령 몇 개의 차단만으로 비밀 제거를 보장하지 않는다. 히스토리 비활성화·삭제와 기록 범위를 도움말에서 설명한다.

autocommit 기본안은 **켜짐, 항상 표시**다. 명시적 거래 중 `exit`는 대화형에서 미완료 거래를 보여 주고 commit/rollback/계속 중 선택하게 하며 기본 선택은 계속이다. 비대화형 정상 종료는 활성 미commit 거래의 rollback을 요청하고 확인한 상태를 보고하며 몰래 commit하지 않는다. 연결 유실·강제 종료로 확인하지 못했거나 commit 결과가 불명확하면 rollback 완료라고 표시하지 않는다. 서버의 미commit 세션 정리와 이미 영속화된 commit의 결과는 구분한다. 초기 DDL이 DML 거래와 함께 허용되지 않는다는 기존 계약도 에러와 도움말에서 설명한다.

### 8.3 스크립트와 자동화

```text
ax sql --context staging-orders --file check.sql --on-error stop --format json
ax config explain query.timeout --context prod-orders --format json
ax logs --context prod-orders --level error --since 30m --format jsonl
ax operation wait OP-38 --context prod-orders --timeout 5min
```

비대화형은 실패 시 중단을 기본으로 한다. 중단은 “앞에서 commit한 문장까지 원복”을 의미하지 않는다. 스크립트는 실행한 문장·실패 위치·마지막 확인 거래 상태를 반환한다. 단일 거래 옵션을 제공할 때는 해당 문장들이 모두 이를 지원하는지 설명하고 DDL·외부 효과를 포함한 허위 원자성을 약속하지 않는다.

기계 출력은 명시적으로 선택하며 locale·터미널 폭·색상·진행 메시지에 영향받지 않는다. stdout에는 선택한 데이터/결과만, stderr에는 진척과 사람용 진단을 보낸다. JSON 결과에는 성공/실패·미완료·일부 결과·결과 불명·권한/미지원·관련 ID가 구분돼야 한다. 큰 수의 정밀도와 타입 정보도 보존한다. 공개 출력에는 schema version과 optional field 처리 규칙을 둔다.

`json`은 유한 요청의 단일 결과 문서이며 여러 JSON 문서를 구분 없이 이어 붙이지 않는다. 대량·연속 출력은 `jsonl`에서 타입 정보, 문장/결과 집합 ID, 순서와 행, 문장 완료, 유한 요청의 최종 결과를 구분하는 레코드로 제공한다. 정확한 필드명은 후속 명세에서 정한다. **최종 결과 레코드 없이 끊긴 유한 출력은 완료가 아니다.** `--follow`처럼 열린 스트림은 관측 범위와 공백을 표시하고 전체 이력 수집 완료를 주장하지 않는다. CSV 같은 데이터 전용 출력에는 별도 완료 receipt나 CLI 종료 결과를 확인하는 절차가 필요하다.

출력 잘림·디스크 부족·broken pipe는 결과 전달 실패로 기록하고 CLI가 정상적으로 종료 코드를 반환할 수 있으면 nonzero로 끝낸다. 이때 서버에서 확인된 commit을 실패로 바꾸지 않는다. **결과 전달 상태, SQL/작업 결과, 거래 효과**를 별도 필드로 유지한다. 다음 문장은 전송하지 않고 이미 실행 중인 요청은 확인 가능한 효과만 보고한다. 자동화는 파일 존재나 일부 행의 수신만으로 성공 처리하지 않으며, 최종 결과의 성공 상태와 반환받을 수 있는 CLI 종료 결과를 함께 확인한다.

종료 코드는 전체 요청의 결과 종류를 안정적으로 구분하고, 오류 코드·거래 효과·재시도 범위는 상세 결과로 제공한다. 정확한 정수 배정은 공개 CLI 명세에서 확정한다. async 동작은 `accepted + operation ID`와 `completed`를 구별한다. 기다리기 명령의 timeout은 서버 작업 취소가 아니다. 재실행 전 operation ID로 현재 결과를 찾을 수 있어야 한다.

**접수 응답 자체가 유실되면 operation ID도 모를 수 있다.** 재시도 가능한 변경 작업은 전송 전에 client가 보존한 제출 키로 접수·결과를 조회할 수 있는지 capability로 알린다. 이를 지원하는 작업은 동일 키·동일 대상·동일 내용의 중복 제출을 하나의 작업에 연결하고, 같은 키의 다른 내용은 거절한다. 키의 권한 범위, 대상 identity/generation, 내용 동일성, 재시작 후 조회 가능성, 중복 방지·결과 보존 기한을 명세한다. 접수 기록과 실제 효과 사이의 장애도 인수 시험 대상이며 ID만 붙였다는 이유로 exactly-once를 주장하지 않는다.

조회 불가·보존 만료·권한 제한·아직 접수 여부 미확정은 미실행의 증거가 아니다. 지원하지 않는 작업이나 보장 기한을 지난 요청은 결과 불명과 수동 확인 경로를 제공하고 자동 재제출하지 않는다. 일반 SQL request ID에 이 중복 방지 의미를 자동 부여하지 않는다. 작업의 실행 상태·관측 확실성·취소 요청 상태도 분리한다. 취소 접수와 실제 취소 완료가 다르며, 취소와 완료가 경합하면 확인된 실제 효과를 보고한다.

자동화는 대상 context를 명시해야 하며 사용자 PC의 최근 선택에 의존하지 않는다. production이라는 색상 표시는 권한 검증을 대신하지 않는다. 암호를 인수에 넣는 예제를 기본 안내로 쓰지 않고 인증 저장소·프롬프트·권한이 제한된 자격 증명 경로를 제공한다. 인증서 검증을 끄는 것이 첫 연결 문제의 기본 해결법이어서는 안 된다.

### 8.4 취소와 실행 계획

Ctrl-C는 먼저 현재 요청 취소를 시도하고 결과를 기다린다. 편집 취소, 요청 취소, 거래 rollback, 연결 종료를 별개 행동으로 보여 준다. 재접속 성공을 이전 거래 복구 성공처럼 표시하지 않는다. query plan 조회는 기본적으로 실행하지 않으며, 실제 실행 통계를 얻는 동작은 읽기 쿼리라도 비용이 있고 DML은 변경을 수행할 수 있다는 사실을 실행 전에 명시한다.

plan 화면에는 선택한 경로·추정/실제 행 수·비용과 시간의 차이·대기·메모리·읽은 저장 매체·통계 시점을 보여 준다. 관측되지 않은 원인을 자동으로 단정하지 않고, 전후 plan 비교와 근거 있는 권장 확인을 제공한다.

## 9. 관리 화면의 최종 형태

관리 화면은 CLI의 명령 버튼 모음이 아니라 사용자의 질문 순서로 구성한다. 동시에 화면에서만 가능한 필수 운영 기능을 만들지 않는다. 기본 업무는 CLI/관리 인터페이스에서 같은 결과와 권한으로 수행할 수 있고, 공개 조회는 SQL로도 접근한다. 서버 시작 전 상태처럼 SQL이 불가능한 업무까지 억지로 SQL에 넣지는 않는다.

다음은 **가상 데이터로 만든 화면 구성 예시**이며 운영 화면의 실제 측정값이 아니다.

```text
XADB      prod / orders / db-a       operator     관측 14:32:12 +09:00
개요 | 활동·쿼리 | 데이터·객체 | 설정 | 이벤트·로그 | 작업 | 접근 관리

서비스: 준비됨 · 쓰기 가능     주의: 요청 지연 증가     관측: 최신
가장 먼저 볼 일
  주문 조회 지연 증가      14:27 이후 / 관련 쿼리 2개 / 요청 18개 대기
  설정 변경 C-41          저장됨 / 재시작 대기 / 현재 서비스는 기존 값

업무 추세 [최근 15분] [이전 15분과 비교]
  지연 분포 · 처리량 · 오류 · 대기      각 지표에 구간/단위/수집 범위

최근 변화
  14:28 C-41 설정 저장       14:27 Q-18 plan 변경 관측

다음 이동
  [대기 요청 보기] [Q-18 쿼리 상세] [C-41 변경 상세] [같은 조회의 SQL]
```

상태등 하나로 “모두 정상”이라고 결론내리지 않는다. 서비스 준비 상태, 요청 실패, 자원 압박, 관측 신뢰도를 별개로 보여 준다. 원인으로 확인되지 않은 설정 변경은 “관련 시점의 변화”라고 표시한다. 기준선이 없으면 이전과 비교할 수 없다고 표시한다.

| 화면 | 기본 내용 | 중요한 행동 |
|---|---|---|
| 활동·쿼리 | 실행/대기/idle 구분, query fingerprint, 앱·사용자, 기간별 비용 | 요청 조사, 제한된 cancel, 추정/실행 plan 구분 |
| 객체 | 정의·행/용량 추정 여부·권한·의존·배치·작업 상태 | 정의 복사, 관련 쿼리·이벤트, 변경 영향 확인 |
| 설정 | 유효 값·출처·저장/대기·적용 시점 | 설명, 검증, 변경안 비교, 이력 |
| 이벤트·로그 | 시간·심각도·분류·코드·빈도·영향 | 사건 펼치기, 관련 요청, 수집 공백 확인 |
| 작업 | 요청자·대상·단계·진척·최근 변화·취소 가능성 | 이어 보기, 기다리기, 허용된 취소, 결과 확인 |
| 접근 관리 | 사용자·역할·유효 권한·권한 출처 | 최소 역할 부여, 감사 확인, credential 관리 |

개요 → 상세 → 로그로 이동해도 시간 범위·환경·request ID가 유지된다. 공유 가능한 조사 참조는 권한을 우회하지 않는다. 시간대는 명시하며 원본 시각을 보존하고 화면 표시 시간대를 바꿀 수 있다. 한국어/영어 설명을 제공하되 명령·코드·기계 필드·숫자 의미는 번역에 따라 달라지지 않는다. 키보드 탐색, 화면 읽기 도구, 색각 차이, 좁은 화면에서도 핵심 상태와 행동이 전달돼야 한다.

빈 화면도 설계한다. 최초 연결은 “수집 시작 전”, 권한 제한은 “볼 수 없음”, 지원하지 않는 기능은 “이 버전에서 미지원”, 보존 기간 밖은 “보존 범위 밖”으로 안내한다. 빈 그래프와 0건만 남기지 않는다.

## 10. 사용자가 끝까지 완수하는 대표 여정

### A. 설치 후 첫 정상 접속

설치 → 대상 이름·데이터 위치·인증 선택 → 초기 설정 검사 → 서버 준비 상태 → 연결 → 첫 SQL → 연결 설정 재사용까지 하나의 안내로 제공한다. 이미 관리 중인 DB 경로와 충돌하면 생성 작업을 시작하지 않는다. DEV2 같은 SQL 없는 사내 버전에는 해당 capability와 사용 가능한 직접 검증 경로만 안내한다.

`xadb doctor`는 접속 실패를 DNS/주소·네트워크·TLS·인증·권한·서버 준비 상태로 나눠 **실제로 확인한 구간**을 보여 준다. 인증 정보가 틀렸다는 추측으로 모든 실패를 설명하지 않는다. 마지막은 “접속 성공, 사용자/DB/권한/거래 모드 확인”이며 단순 process started가 아니다.

### B. 설정 변경이 정말 적용됐는지 확인

설정 검색 → 설명·출처 확인 → 변경안 → 검증/영향 → 저장 또는 적용 → 현재/대기 비교 → 새 세션 또는 재시작 후 확인으로 이어진다. 변경 전후 관측을 나란히 보여 주되 변화가 설정 때문이라고 자동 단정하지 않는다. 되돌리기는 이전 값을 이용한 새 변경이며 이미 종료된 세션이나 처리한 업무를 과거로 돌린다고 표현하지 않는다.

### C. “주문 조회가 갑자기 느립니다”

시간 구간·앱 선택 → 상위 쿼리 → 요청 시간 분해 → 관측된 blocker/자원/plan → 관련 이벤트·변경 → 가능한 조치 → 조치 후 비교로 이어진다. 처음부터 여러 V$와 로그 파일명을 외워 SQL을 조립하게 하지 않는다. 전문가에게는 같은 정보의 SQL과 세부 필드를 제공한다.

취소는 특정 실행에만, 세션 종료는 그 세션과 미완료 거래에 어떤 효과가 있는지 표시한다. 자동으로 blocker를 죽이거나 설정을 바꾸지 않는다. 샘플링으로 실제 요청을 보존하지 못했다면 query 요약만으로 특정 실행을 확정하지 않는다. 원인이 불명하면 다음에 필요한 제한된 수집을 제안한다.

### D. 새벽에 서버가 준비되지 않습니다

`xadb status`에서 준비 실패·단계·경과·최근 진척 → 로컬 초기 메시지 → 설정/자원 오류 → 수정안 검증 → 재시도 → 서비스 준비 확인으로 이어진다. 진척을 알 수 없으면 퍼센트나 ETA를 지어내지 않고 마지막 관측과 정체 시간을 표시한다. 로그 저장도 실패했다면 확보된 fallback과 누락 가능 범위를 알린다.

### E. 지원팀에 인계합니다

사건 선택 → 조사 시간·대상 확인 → 묶음 내용·민감 정보 확인 → 로컬 생성 → 수집 성공/실패·공백 검사 → 사용자가 선택한 전달로 끝난다. 묶음만으로 확인할 수 있는 사실과 추가 질문을 명시한다. 인터넷·AI 연결·지원 계정 없이 기본 자료 생성과 열람이 가능하다.

### F. 디스크 저장 테이블을 운영합니다

논리 테이블 선택 → DISK 파티션 배치 → local/global index 범위 → 자원·접근 추세 → 변경 작업 영향 → 진행·결과 확인으로 이어진다. 같은 테이블인데 매체별 도구를 따로 배워야 하지 않는다. “메모리에 있음”을 “비영속”으로 표현하지 않으며 global index의 논리 범위와 물리 저장 매체를 분리한다.

### G. 야간 작업을 자동화합니다

대상 context와 변경 조건 지정 → 사전 검사 → 지원되는 제출 키 보존 → 명시적 실행 → operation ID 기록 → 완료 또는 결과 불명 분기 → 다음 실행에서 결과 조회로 이어진다. 터미널 접속이나 접수 응답이 끊겨도 선언한 조회 범위 안에서 같은 작업을 찾아야 한다. 찾을 수 없으면 미실행으로 간주하지 않는다. CSV 파일만 남기고 중간 SQL 오류나 결과 전달 실패를 성공 처리하는 흐름을 허용하지 않는다.

### H. 기존 업무를 XADB로 옮깁니다

객체·타입·SQL/PSM 조사 → XADB 대응과 변환 불가 항목 확인 → 논리 schema/data 이동 → 값·제약·업무 결과 비교 → 차이 해결 → cutover 조건 확인으로 이어진다. 항목마다 원본·변환안·실행 결과·미해결 사유를 연결하고 성공/부분 성공/지원 불가를 구분한다. 선택 동기화는 변경될 데이터와 충돌 정책을 미리 보여 준다. 기존 파일·wire 호환은 요구하지 않지만 기존 업무의 보존과 논리 이관·검증 경험은 [R14 제품 요구](../plans/product-requirements.md)에 따라 제공해야 한다.

## 11. XADB다운 경험: 디스크 데이터도 하나의 객체

경쟁력은 통일된 명령 이름만으로 생기지 않는다. XADB가 지향하는 디스크 저장과 native global index가 **사용자에게 단일 논리 데이터 모델**로 보여야 한다.

| 정보 | 최종 표현 |
|---|---|
| 논리 객체 | `sales.orders` 하나를 기준으로 정의·권한·질의·사건을 연결 |
| 데이터 배치 | 파티션별 DISK, 상주량·사용량·추정 여부를 각각 표시 |
| index | global/local 범위, unique 여부, DISK 매체를 별개 속성으로 표시 |
| 조회 경로 | 어떤 파티션·index·매체를 접근했는지 plan에서 설명 |
| 변경 영향 | 관련 쿼리·index·잠금·서비스 중단 가능성을 미리 표시 |
| 실행 상태 | 준비/진행/검증/완료/실패/결과 불명을 작업에서 동일하게 표시 |

최초 offline 작업은 서비스 중단 범위를 드러내야 한다. 온라인 이동·자동 tiering을 완료 화면에 먼저 그려 놓고 실제 지원으로 오인하게 하지 않는다. 자동 최적화는 근거·예상 영향·한계·되돌릴 조건이 설명될 때 후속 확장으로 검토한다.

<a id="section-12"></a>

## 12. 오류·권한·일관된 결과 언어

오류 경험은 로그와 client 양쪽에서 같아야 한다. 공개 오류는 안정된 XADB 코드, 해당하는 SQLSTATE, 짧은 설명, 세부 근거, 위치, 거래 영향, 재시도 범위, 확실성, 관련 ID와 도움말을 제공한다. 인가된 범위 안에서 동일 사건을 찾을 수 있어야 한다. 내부 파일명·소스 줄·stack은 전문가 상세로 두며 기본 사용자에게 원인 확정처럼 제시하지 않는다.

| 상황 | 사용자가 알아야 하는 것 |
|---|---|
| 문장 오류 | 해당 문장 효과가 되돌려졌는지, 이전 문장과 거래 상태 |
| 거래 충돌 | 거래 전체가 종료됐는지, 재시도 단위는 전체 거래인지 |
| 응답 유실·결과 불명 | 성공/실패를 아직 확정할 수 없음, 확인 수단·보존 기한 |
| 권한 부족 | 작업에 필요한 권한과 신청 경로; 숨겨야 할 객체는 노출하지 않음 |
| 미지원 | 버전·capability상 불가, 가능한 대안과 적용 범위 |
| 설정 충돌 | 검토 이후 바뀐 값·대상과 다시 검토할 부분 |

UNKNOWN을 무조건 rollback 또는 retry로 바꾸지 않는다. 요청 ID로 결과를 조회하는 기능이 아직 없거나 기록 보존이 끝났다면 그 제한을 밝힌다. “재시도 가능”은 현재 문장, 거래 전체, 읽기 재조회 중 무엇인지 알려야 한다. 이 원칙은 기존 커널의 오류/거래 계약을 따르며 새로운 실패 효과를 발명하지 않는다.

권한은 일반 사용자·관측자·운영자·설정 관리자·보안/감사 담당·지원 진단의 업무로 나눈다. 정확한 role 이름과 조합은 후속 명세에서 정하되, 일상 관측 때문에 최고 권한을 요구하지 않는 것을 목표로 한다. 자신의 세션/쿼리와 타인의 SQL 원문 열람은 별개다. 콘솔에서 숨긴 정보가 공개 뷰·CLI JSON·로그·묶음에 다시 노출되지 않아야 한다.

AI 보조는 선택 기능이다. 관측 사실과 가설을 나누고 근거 참조를 제공하며 변경은 사용자가 검토한 행동으로 남긴다. 기본 상태 조회·설정 설명·메시지 검색·오류 안내·지원 자료 생성에는 모델 연결이 필요하지 않아야 한다.

## 13. 운영 업무와 외부 도구의 완결성

| 업무 | 경쟁 제품에 뒤처지지 않기 위한 경험 기준 |
|---|---|
| 시작·정지·재시작 | 준비 상태와 연결/거래 drain을 설명, 강제 종료와 구분, 완료 확인 |
| backup/restore | 실행 성공·검증 성공·복원 가능성 증거를 구분, 대상·덮어쓰기 영향·진행 표시 |
| import/export | 형식·encoding·NULL·타입·오류 행·부분 성공·재개 가능성을 명시 |
| migration·데이터 비교 | 객체별 대응·변환 불가·검증 차이·선택 동기화 영향·전환 조건을 명시 |
| 복제·전환 | 역할·관측 시각·지연 단위·연결/적용 상태, 전환 전제와 실제 결과 표시 |
| 업그레이드 | capability·설정·공개 뷰·driver·저장 형식 영향과 필요한 중단 설명 |
| 애플리케이션 연결 | native/JDBC/ODBC에서 metadata·오류·timeout·cancel 의미 일치 |
| 일반 SQL 도구 | 선언한 JDBC/ODBC subset으로 객체 탐색·바인딩·결과 표시가 실제 동작 |
| 관측 연계 | 문서화한 metrics·JSON 메시지·관련 trace ID, 실제로 시험한 연계 조합 공개 |

| 외부 운영 체계 | SNMP·알림·관리/directory 연계의 기능 대응과 자격 증명·실패 상태 공개 |
| 자동 운영 | CLI/관리 인터페이스에 기능·권한·실패 의미 제공, 불투명한 UI 전용 기능 방지 |
| 매뉴얼 | 작업 안내·개념·참고서·문제 해결을 구분, 설치 버전에 맞는 오프라인 도움말 |

이 표는 모든 기능이 현재 지원된다는 선언이 아니다. 지원하기로 명시한 업무의 leaf가 구현·검증돼야 한다. 외부 도구나 프로토콜의 이름을 나열한 것만으로 연결 지원을 주장하지 않는다. 특정 OTel/Prometheus exporter 또는 IDE 지원 조합은 후속 공개 범위와 시험으로 확정한다.

기본 도움말은 “메모리 사용이 높다”, “설정을 바꿨는데 그대로다”, “로그가 안 보인다”, “연결은 되는데 권한이 없다”와 같은 작업 안내에서 시작한다. 각 항목에 증상 → 확인 → 판단 → 조치 → 결과 확인을 둔다. 참고서의 모든 공개 설정·뷰·코드에는 도입 버전·권한·예시·관련 작업 안내가 연결돼야 한다.

## 14. 개발 순서·공개 계약과의 관계

이 기획의 최종 경험을 만들기 위해 기존 **DEV0 → DEV1 → DEV2 → DEV3 → DEV4 → DEV5 → DEV6** 기본 경로를 유지한다. COMM은 DEV1 뒤, PART는 DEV3 뒤, NG는 PART 뒤의 독립 경로이며 SQL과 서로의 완성을 기다리지 않는다. DEV7/8은 기존 DAG의 기능별 선행 관계를 따른다. 현재 단계에서 생기는 정보를 나중에 같은 언어로 보여 줄 수 있도록 경험 의무를 적립한다.

| 기존 단계 | 그 단계의 경험 관점 준비 | 아직 약속하지 않는 것 |
|---|---|---|
| DEV1 | ID·오류·단위·확실성·메시지 어휘와 기록 의무 | 전체 사용자 CLI·관측 화면 |
| DEV2/3 | SQL 없는 상태·진행·설정·오류 관측, DISK 개념 일치 | SQL 시스템 뷰·네트워크 접속 |
| DEV4 | embedded SQL의 프롬프트·문장 결과·기본 metadata/도움말 | 최종 쿼리 분석·과거 통계 전체 |
| DEV5 | 서버 identity·접속·인증·세션·요청·운영 메시지 | 미구현 HA·무중단 작업 |
| DEV6 | driver/CLI 오류·metadata·스크립트·자동화 일치 | 모든 외부 도구 지원 |
| DEV7/8 | 쿼리 분석 확장·운영 작업·메시지 검색·이력·관리 화면 구체화 | 미검증 기능의 출시 가능 선언 |
| PART/NG | 파티션·global 범위·배치를 공개 경험으로 연결 | core PASS만으로 SQL 업무 완료 |
| DEV9 | 선언한 제품 기능의 사용자 여정 평가·운영 인수 | 이번 기획 문서만으로 gate 통과 |

위 대응은 작업 순서 변경이나 task 완료 표시가 아니다. 기획 JSON의 stage 참조는 이후 구현 계획에 연결하기 위한 것이다. 정확한 leaf 작업과 단계 내부 순서는 그 시점의 실제 의존성에 따라 별도로 정한다.

공개 설정·명령·뷰·메시지 코드·기계 출력은 **최초 안정 릴리스부터** [현재 same-major 단방향 호환 정책](../policies/version-compatibility-policy.json)을 적용한다. 이전 안정 릴리스 XADB client/script가 새 XADB server/CLI에서 기존 의미로 동작해야 한다. 사내 배포는 매번 새 DB·fixture로 구축하며 이전 사내 버전의 호환·변환을 요구하지 않는다. 사람용 문장 개선과 기계 의미 변경을 구분한다. 고객에게 이미 공개한 enum의 추가도 exhaustive consumer에 미치는 영향을 판단해야 하며 무조건 안전하다고 보지 않는다. 삭제·이름 변경은 조용히 수행하지 않는다.


이번 제안은 기존 kernel contract·버전 정책·출시 gate를 변경하지 않는다. 채택 후 공개 명세로 승격할 항목은 JSON에 추적하며 그 전에는 문법·이름의 가변성을 명시한다.

## 15. ‘세련된 경험’을 판정하는 기준

다음은 **미실행 사용성·제품 인수 계획**이다. 문서 검증 성공, 화면 목업, DEV0 하네스 시험으로 PASS를 대신할 수 없다. 시간 목표는 사용자 연구로 보정할 제안이며 서버 처리 성능 SLA가 아니다.

평가 종류는 사용자 과제 평가, 결정적 제품 인수 시험, 둘을 각각 수행하는 혼합 평가로 구분한다. 사용자 과제의 성공률이 제품 오류·복구 시험을 대신하지 않으며 자동 시험 통과가 사용성 검증을 대신하지 않는다. JSON의 각 사례에 평가 종류·관련 개발 단계·필요 capability를 기록한다. 단계 참조는 준비·평가 지점이며, 모든 하위 단계가 전체 콘솔 여정을 구현해야 한다는 뜻이 아니다.

첫 사용자 과제 평가는 DBA 5명, 개발자 5명, 운영/플랫폼 담당 5명을 목표로 하며 초보/숙련도를 기록한다. 경쟁 비교는 같은 fixture·권한·과제와 공개 기본 도구에서 실시하고, 추가 도구 사용과 학습 시간을 별도로 적는다. 소규모 표본의 과제 성공률로 시장 전체의 우월성을 주장하지 않는다.

| UX-26 | 유한 JSON/JSONL·CSV 출력의 중간 오류·잘림·broken pipe·commit 후 출력 실패를 자동화가 구분 | 일부 행/파일만으로 성공 처리·완료 레코드 없는 유한 스트림 성공·출력 실패를 rollback으로 보고 |
| UX-27 | 검토 후 context 변경·객체/세션 재생성·권한 철회·설정 revision 변경 시 오래된 변경/cancel 거절 | 이름이나 재사용 ID만 같다는 이유로 다른 대상에 변경·취소 실행 |

UX-07은 같은 대상·권한·workload·counter 초기화 구간에서 비교하고 갱신 오차 기준을 측정 전에 정한다. UX-17의 사내 배포는 `NOT_REQUIRED_INTERNAL_FRESH_BUILD`, 이전 고객 기준선이 없는 안정 릴리스 후보는 `NOT_APPLICABLE_NO_RELEASE_BASELINE`로 구분하며 둘 다 교차 버전 PASS로 계산하지 않는다. 이 계획의 실제 실행 상태는 계속 `NOT_RUN`이다.

UX-23의 허용 비용 수치는 측정 전에 workload와 함께 합의한다. 시간 목표가 있는 UX-01/02/04/13은 동일한 준비 조건을 기록하고, 성공률·중간값·상위 지연·실패 이유·도움 요청 횟수를 함께 남긴다. UX-03/06/08/16처럼 오판의 영향이 큰 과제는 정답을 화면에서 검증할 수 있게 하고, 평가 중 한 번이라도 잘못된 확신을 유발하면 설계를 수정한다.

<a id="section-16"></a>

## 16. 기획 결정과 후속 확인

지금 권고하는 방향은 **하나의 `xadb` 입구, 공개 운영 뷰, 설명 가능한 설정, 사건 중심 message logging, 일관된 오류·작업 상태, 디스크 파티션 객체 경험, 기본 진단의 자체 완결성**이다. JSON의 D-01–D-10에 추적한다. CLI·콘솔·SQL은 각각의 장점을 살리되 같은 업무의 결과와 권한이 일치해야 한다.

후속 확인이 필요한 것은 XADB의 구체적인 SQL·업무/도구 목록, 기본 보존 기간과 용량, 허용 관측 비용, 운영 조직의 권한 분리, audit 적용 범위, 관리 화면 배포 방식이다. 이 항목들은 없는 정보를 채워 넣어 확정하지 않았다. 화면과 명령의 예시는 방향을 검토할 만큼 구체화했으며, 세부 문법·공개 view column·설정 값은 채택 후 별도 제품 명세에서 확정한다.

최종 평가는 “property가 몇 개이고 V$가 몇 개인가”가 아니라 **사용자가 필요한 질문에 답하고, 조치의 영향을 이해하고, 결과를 검증하고, 다음 사람에게 정확히 인계할 수 있는가**다. 그 깊이를 SQL과 진단 자료로 유지하면서 일상 경로를 짧게 만드는 것이 XADB가 지향할 경험이다.

## 17. 인터페이스 리뷰와 매뉴얼 착수 범위

2026-10-18 리뷰에서 다음 설계상의 빈틈을 수정했다. 수정 반영은 구현이나 제품 인수 시험 통과를 뜻하지 않는다. 기존 개발 순서·커널의 거래 효과·사내 호환 비요구 정책은 유지한다.

| ID | 발견한 문제 | 반영한 수정 | 연결 인수 계획 |
|---|---|---|---|
| IR-01 | 접수 응답 유실 시 작업 중복 실행 가능 | 전송 전 보존한 제출 키·조건부 중복 방지·조회/보존 경계와 결과 불명 처리 | UX-10 |
| IR-02 | 진단 자동 원복이 동시 설정 변경을 덮어쓸 수 있음 | 소유 수집만 해제하고 현재 기본값·다른 수집 보존 | UX-12, UX-18 |
| IR-03 | 출력 중단과 서버 거래 결과의 혼동 | 유한 출력 완료 표식과 전달/동작/거래 상태 분리, 확인되지 않은 rollback 표시 금지 | UX-09, UX-26 |
| IR-04 | 검토 후 바뀐 대상이나 재사용 ID에 변경·취소 가능 | 대상 identity/generation·revision·권한·유효기간 재확인 | UX-27 |
| IR-05 | 입력 출처 우선순위와 임시 값 만료 의미 누락 | 범위와 출처 우선순위 구분, 가려진 값·다음 시작·만료 지원 범위 명시 | UX-18 |
| IR-06 | 외부 로그 전송을 과거 검색 지원으로 오해 | sink 전송과 검색 capability·보존/공백·이어보기 범위 분리 | UX-11 |

| IR-08 | 감사 사전 확인 이후 실패의 결과 의미 미정 | 동작 효과와 감사 기록 상태를 별도로 보고 | UX-22 |

문서 검사기는 결정·근거·개발 단계·제품 요구·인수 사례의 참조와 중복 ID, Markdown/JSON 표의 일치, 미실행 표시를 검사한다. 이 검사로 작업 중복 방지·권한 제한·trace 종료가 실제 동작한다고 판정하지 않는다.

**이 문서는 경험 기획의 기준안이며 완결된 공개 인터페이스 명세는 아니다.** 이를 바탕으로 매뉴얼의 개념·업무 흐름·오류 대응 초안을 시작할 수 있다. 실행 가능한 참고서로 확정할 때는 기능별로 다음을 먼저 정한다.

1. 정확한 명령·SQL 구문·옵션·기본값·설정별 적용 범위와 출처, 뷰의 열·타입·NULL·단위·관측 의미.
2. 결과/오류 필드·enum·schema version·종료 코드, 취소·거래 효과, 작업 조회·중복 방지 범위와 보존 기한.
3. 권한·민감 정보 처리, 지원 capability·도입 단계/버전, 독립 기대 결과와 실행할 인수 사례.

아직 정하지 않은 값은 제안 또는 미확정으로 표시한다. 문법 예제를 실행 검증된 예제로 승격하려면 해당 기능의 실제 구현·시험 증거를 연결한다. 모든 후속 명세가 끝날 때까지 DEV1–3을 기다리게 하지 않고, 각 기능 구현 전에 필요한 계약을 확정한다.

매뉴얼 초안 0.2에서 [기계 출력·설정·뷰·driver의 상세 제안](user-manual-draft.md)과 [리뷰·인수 추적](manual-review.md)을 보강했다. 이 보강의 필드명·encoding·상태표는 구현 전 검토할 제안이며, 이 문서의 경험 인수 계획과 기존 커널·버전 계약을 유지한다.
